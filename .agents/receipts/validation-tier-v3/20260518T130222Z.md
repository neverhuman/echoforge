# validation-tier-v3 — V3 (benchmarked) promotion gate evaluator (SCAFFOLD)

- Timestamp: `20260518T130222Z`
- Packet: `validation-tier-v3` (per `FUCKIT.md` roadmap; SCAFFOLD variant
  that ships the gate logic without requiring the upstream metrics
  producer)
- Scope: `crates/echoforge-validate/src/tier_v3.rs` (new),

## Why

`docs/validation-tiers.md` pins V3 = "benchmark suite with stable
metrics (Pd/Pfa, range/Doppler error, OSPA on tracks)". The
schemas-side V3 alias `benchmarked` is already enumerated in
`schemas/common.schema.json#/$defs/validation.tier`, but
`crates/echoforge-validate/src/report.rs` has only V0/V1/V2 wired into
`TierAchieved` and `promotion_gate(...)`.

This packet lands the **V3 GATE LOGIC** as an additive evaluator that:

1. accepts a pre-computed `V3MetricObservation` plus a
   `V3MetricThresholds` envelope, and
2. produces a strict pass / fail `V3GateReport` listing every metric
   that violated its threshold.

The **upstream metrics producer** (a live benchmark campaign that
computes pd/pfa/range/doppler/OSPA from a sagittasbr-computed RCS
truth) is a separate concern. `sagittasbr-adapter` is landing as a
stub in parallel; `radar-clutter-module` is already done. This packet
ships only the threshold evaluator so the V3 gate logic is in place
when the real benchmark output stream comes online.

Per the FUCKIT.md.done cross-tip resolution that separates
method-ceiling (fidelity F0–F5) from evidence-tier (validation V0–V5),
the V3 gate is purely an evidence-tier evaluator and does NOT interact
with the `fidelity_class` axis. The validate crate's V0/V1/V2 gate in
`crates/echoforge-validate/src/report.rs` is also intentionally
untouched — V3 is purely additive.

## Files Changed

- `crates/echoforge-validate/src/tier_v3.rs` (new, 17.9 KB)
  - Public types:
    - `pub struct V3MetricThresholds { pd_min, pfa_max,
      range_error_max_m, doppler_error_max_mps, ospa_max }` — every
      field is `f64`. Provides `default_roadmap()` constructor with
      conservative starting values (`pd_min=0.85, pfa_max=0.01,
      range_error_max_m=5.0, doppler_error_max_mps=1.0, ospa_max=10.0`)
      anchored on the roadmap entry's wording.
    - `pub struct V3MetricObservation { pd, pfa, range_error_m,
      doppler_error_mps, ospa_distance, sample_count }` — first five
      are `f64`, last is `usize`. `sample_count` is reported alongside
      the gate result so downstream consumers can reason about
      confidence.
    - `pub enum GateStatus { Pass, Warn, Fail }` — re-exported from
      `lib.rs`; serialized lowercase (`"pass"|"warn"|"fail"`). The V3
      evaluator never emits `Warn` (it is strict pass/fail by
      construction); the variant exists to keep the type future-proof
      for callers that might wrap the gate with degraded-mode
      semantics.
    - `pub struct V3GateReport { tier: &'static str, status,
      failures: Vec<String>, observation, thresholds }` — `tier` is
      pinned to the literal string `"V3"`; callers wanting the
      schema-alias form may map via `tier_alias_benchmarked()`.
      `failures` lists stable identifiers (`"pd"`, `"pfa"`,
      `"range_error"`, `"doppler_error"`, `"ospa"`) so machine
      readers can pattern-match.
  - Public functions:
    - `pub fn evaluate_v3_gate(thresholds, observation) ->
      V3GateReport` — checks each metric against its threshold using
      `>=` for pd and `<=` for the four error metrics. Builds the
      `failures` vec in stable order (pd, pfa, range, doppler, ospa).
      NaN observations are treated as failures (`NaN >= 0.85` is
      `false`); see test `nan_pd_is_treated_as_failure`.
    - `pub fn evaluate_v3_from_benchmark_json(thresholds, path) ->
      Result<V3GateReport, ValidateError>` — convenience reader. Reads
      a `benchmark_report.json` (per
      `schemas/benchmark_report.schema.json`, whose
      `additionalProperties: true` lets a producer attach a
      `metrics: { pd, pfa, range_error_m, doppler_error_mps,
      ospa_distance, sample_count }` block), extracts the six expected
      fields, and runs the gate. Friendly `ValidateError::Schema` when
      the metrics block is absent or any required field is missing.
    - `pub const fn tier_alias_benchmarked() -> &'static str` —
      returns the schema-alias form `"benchmarked"` so callers that
      surface the schema-aligned vocabulary can do so without
      hard-coding the string.
  - Tests (12 in this module — well above the >=6 packet floor):

## Notes / Risks / Follow-ups

- **This is the V3 GATE LOGIC only.** The threshold evaluator is in
  place; the upstream metrics producer (a real benchmark campaign
  that computes pd/pfa/range/doppler/OSPA from a sagittasbr-computed
  RCS truth) is a separate concern handled in different packets. A
  follow-up packet should:
  - Run the live campaign once `sagittasbr-adapter` is no longer a
    stub.
  - Confirm the live campaign's `benchmark_report.json` exposes the
    `metrics.{pd, pfa, range_error_m, doppler_error_mps,
    ospa_distance, sample_count}` block consumed by
    `evaluate_v3_from_benchmark_json`.
  - If the producer chose different field names or units, add an
    adapter (do not silently rename in this evaluator; the gate is
    intentionally stable).
- **Strict pass/fail by construction.** The V3 evaluator never emits
  `GateStatus::Warn`. The variant exists in the enum so callers that
  want to wrap the gate with degraded-mode semantics (e.g. "warn
  when `sample_count < N`") have a clear extension point. The
  packet boundary says the evaluator must not silently upgrade /
  downgrade tier strings; the same rule applies to its status.
- **NaN handling is intentional.** Every comparison is written
  `observation.metric >= threshold` (or `<=`), with the boolean
  negated when needed. `NaN >= x` is always `false`, so a NaN
  observation is recorded as a failure rather than silently passing
  (see test `nan_pd_is_treated_as_failure`). If a future producer
  wants to treat NaN as "unknown — warn" instead of "fail", add the
  policy in a wrapper, not in this evaluator.
- **`report.rs` is untouched.** Per packet boundary, the V0/V1/V2
  gate in `crates/echoforge-validate/src/report.rs` is not modified.
  V3 ships as an independent evaluator; `TierAchieved` is not
  extended to include `V3` because the existing
  `TierAchieved::parse` / `as_str` round-trip would silently break
  the V0/V1/V2 contract if a `V3` variant were added. A future
  packet that wants to surface V3 through `ValidateReport` should
  introduce a `ValidateReportV2` (or analogous) rather than mutating
  the existing enum.
- **`tier_alias_benchmarked()` rather than auto-aliasing.** The
  `V3GateReport.tier` field is pinned to the string `"V3"` (the
  ladder-vocabulary form). Callers that need the schema-alias form
  (`"benchmarked"`) call `tier_alias_benchmarked()` explicitly. This
  keeps the gate output stable regardless of which vocabulary the
  consumer prefers and avoids the silent-rename failure mode.
- **Concurrent packet coexistence verified.** When I read
  `lib.rs` after writing `tier_v3.rs`, the `validate-fidelity-rollup`
  packet had already landed `pub mod fidelity_rollup;` plus its
  re-export block. I preserved those edits exactly and added my own
  `pub mod tier_v3;` line and re-export block adjacent. The two
  modules do not import each other and have no namespace overlap
  (`GateStatus` is owned by `tier_v3`; `FidelityFloor` /
  `FidelityRollup` are owned by `fidelity_rollup`).
- **Boundary test pinned.**
  `v3_gate_does_not_mention_v0_v1_v2_strings` exists so a future
  refactor that accidentally couples V3 back to the V0/V1/V2 string
  vocabulary fails the test rather than silently changing the gate's
  contract.
- **Convenience reader uses the existing schema.**
  `schemas/benchmark_report.schema.json` already declares
  `additionalProperties: true`, so a producer attaching a `metrics`
  block does not require a schema bump. If a follow-up packet wants
  to make the `metrics` block schema-required for V3-tier benchmark
  reports, that belongs in a separate `benchmark-report-v2` packet
  with its own deprecation window.
