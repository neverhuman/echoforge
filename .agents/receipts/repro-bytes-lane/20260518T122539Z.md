## Scope

- Add a reproducibility-bytes lane that fails on any drift in the
  Monte-Carlo demo output tree across reruns. Two enforcement points:
  - **Rust integration test** —
    `crates/echoforge-dataset/tests/repro_bytes.rs` runs
    `run_monte_carlo_demo` twice into two `tempfile::TempDir` roots
    and sha256-compares every file.
  - **Shell-side recipe** — `just repro` invokes
    `tools/repro_bytes.mjs` which shells out to the released CLI
    (`cargo run -p echoforge-cli --release -- demo monte-carlo ...`)
    twice and does the same byte comparison. Wired through `rtk`.
- Both enforcement points exclude `benchmark_report.md` and
  `benchmark_report.json` from the byte check — those files carry
  wallclock stage timings and throughput measurements that vary
  across runs by design. Their presence/absence is still
  cross-checked, so a file dropping out of the tree across runs is
  still a failure. The exclusion list is kept in lockstep between
  the Rust test (`WALLCLOCK_FILES` constant) and the Node script
  (`WALLCLOCK_FILES` Set); both files cross-reference each other in
  their header comments.

## Files Changed

- `crates/echoforge-dataset/Cargo.toml`

- `crates/echoforge-dataset/tests/repro_bytes.rs` (new)
  - Integration test `dataset_tree_is_byte_stable_across_reruns`:
    runs `run_monte_carlo_demo` twice with identical config (preset
    `low-altitude-fixed-wing-takeoff-v1`, seed `20_260_518`,
    `generated_at = "2026-05-18T00:00:00Z"`, 4 episodes, pulse_count
    8) into two tempdir subroots, walks both trees, computes sha256
    per file, and asserts file-set equality plus per-file hash
    equality. Wallclock-derivative files allowlisted in
    `WALLCLOCK_FILES`.
- `tools/repro_bytes.mjs` (new, Node ESM)
  - Shell-side companion. Argument: workdir (default
    `target/repro-bytes/<preset>`). Shells out to
    `cargo run -p echoforge-cli --release -- demo monte-carlo ...`
    twice into `<workdir>/run-a` and `<workdir>/run-b`, walks both
    trees, sha256-compares every file (minus the wallclock allowlist),
    and prints a JSON summary
    `{ok, run_a_count, run_b_count, compared, mismatches, only_in_a,
    only_in_b, excluded_wallclock}`. Exits 0 on byte-equality, 1 on
    mismatch, 3 on usage / IO / subprocess error.
- `Justfile`
  - Added `repro` recipe: `mkdir -p target/repro-bytes` then
    `rtk node tools/repro_bytes.mjs target/repro-bytes/low-altitude-fixed-wing-takeoff-v1`.

## Validation

- The Rust test runs the same code path as the existing
  `same_seed_and_timestamp_keep_manifest_stable` determinism test in
  `monte_carlo.rs`, but extends coverage from `manifest.json` only to
  the full output tree (54 files across `episodes/`, `products/`,
  `sensor_archetype.json`, `dataset_card.json`, `split_manifest.json`,
  `leakage_report.json`, `records.jsonl`, plus the four static cards).
- The shell test additionally exercises the CLI surface — different
  call path than the in-process integration test, so it would catch a
  regression that lives in CLI flag plumbing rather than the library.
- Wallclock allowlist is 2 entries (`benchmark_report.md`,
  `benchmark_report.json`); both files are inherently non-deterministic
  by design (stage timings, throughput). Any future writer that emits
  a wallclock-derivative file must add itself to the allowlist
  explicitly — failure to do so will surface as a real lane failure.

## Notes / Risks / Follow-ups

- The lane runs `cargo run --release` twice; cold cache adds ~10 s to
  first invocation, warm cache is ~1 s per run. Acceptable for CI but
  not in the lefthook pre-commit hot path; do not wire there.
- The Rust test uses `tempfile::TempDir` so it self-cleans. The shell
  recipe writes under `target/repro-bytes/`; `target/` is already
  `.gitignore`d.
- The exclusion list is the only judgement call here. Two reviewers
  could reasonably disagree on whether `benchmark_report.md` should
  itself be made deterministic (strip timings) vs. excluded as a
  wallclock artifact. I chose exclusion because (a) the file's stated
  purpose is to report performance, (b) the dataset itself is the
  reproducibility-relevant artifact, and (c) any future shift toward
  a deterministic benchmark report can simply remove that entry from
  the allowlist — the test will then start asserting on it.
- Scope guardrails: I did **not** touch `crates/echoforge-radar/*`,
  `crates/echoforge-cli/src/demo.rs`, `crates/echoforge-dataset/src/{campaign,lib}.rs`,
  `schemas/`, `agent/`, `.github/workflows/`, or
  `configs/monte-carlo/airspace-objects-v1.json`. The only file
  modified outside the new test / new tool / new receipt is the
  dataset crate `Cargo.toml` (one-line dev-dep addition) and the
  `Justfile` (recipe addition).
- Follow-up packet candidate: extend the lane to also cover the
  `monte-carlo-campaign` output tree once that surface stabilizes
  (currently the campaign writes a much larger tree and would slow
  the lane considerably; defer until throughput is more important
  than coverage breadth).
