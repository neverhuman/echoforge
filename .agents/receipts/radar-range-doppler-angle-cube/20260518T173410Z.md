# radar-range-doppler-angle-cube — RDA cube primitive

- Timestamp: `20260518T173410Z`

- Scope: `crates/echoforge-radar/src/rda_cube.rs` (new file, 760 lines)

## Why

The radar processing pipeline lacked a canonical 3-D Range-Doppler-Angle
(RDA) representation of a coherent processing interval. The existing
`RangeDoppler` type in `crates/echoforge-radar/src/detectors/` is 2-D
(range × Doppler) and assumes the front end already collapsed channels
into a single beamformed stream. For direction-of-arrival aware detectors
the cube needs to vary the look direction across a discrete steering
grid so detection / classification / tracking can integrate over angle.

This packet lands the RDA cube assembly that:

1. Accepts per-channel IQ samples (`channel_iq[channel][sample]`) and a
   `PhasedArrayManifold` describing the array geometry.
2. Steers across a caller-supplied `AngleGrid` of `(azimuth, elevation)`
   pairs.
3. For each grid cell beamforms with the conjugated ULA steering vector
   (delay-and-sum convention, matching the production
   `DelayAndSumBeamformer` in `beamforming.rs`).
4. Reshapes the beamformed time-series as `n_doppler × n_range`, applies
   a Hann window across slow-time, and runs a per-range Doppler DFT to
   populate the cube cells in power-domain `f32`.

Per correctness gate C2 (local coordination scratchpad 20260518T172000Z) the pipeline
preserves complex IQ through beamforming and through the Doppler DFT;
only the final cube cells are squared-magnitude to match the
`RangeDoppler` (2-D) convention already used by every downstream
detector (`detectors/` consumers expect linear power, not dB).

This unblocks `baseline-detector-classifier-tracker`, which needs an
angle-aware cube to extract per-direction range-Doppler slabs.

## Files Changed

- `crates/echoforge-radar/src/rda_cube.rs` (new, 26.6 KB / 760 lines).
  - Public types:
    - `pub struct AngleGrid { azimuth_deg: Vec<f64>, elevation_deg: Vec<f64> }` —
      the discrete steering grid. Constructors `AngleGrid::new(az, el)`
      and `AngleGrid::azimuth_only(az)` (the single-elevation common
      case). `len()`, `is_empty()`, and `at(index) -> Option<(f64, f64)>`
      decode flat indices in the canonical "elevation slow, azimuth
      fast" order.
    - `pub struct RangeDopplerAngle { range_bins, doppler_bins,
      angle_count, angle_grid, cube: Vec<Vec<Vec<f32>>> }` — the cube
      itself, indexed `cube[angle][doppler][range]` in linear power.
      `RangeDopplerAngle::zeros(range_bins, doppler_bins, grid)`
      allocates a zero-filled cube; `angle_slice(angle_idx)` borrows the
      2-D Doppler × range matrix for one angle.
    - `pub struct RdaPeak { angle_idx, doppler_idx, range_idx,
      magnitude, azimuth_deg, elevation_deg, doppler_hz, range_bin }` —
      the descriptor returned by the peak helper.
  - Public functions:
    - `pub fn build_rda_cube(channel_iq, manifold, angle_grid,
      range_doppler_bins, pri_s, carrier_hz) -> RangeDopplerAngle` — the
      core assembler. Steers per-cell via `steering_vector(...)`,
      beamforms with the conjugated weight, reshapes
      `[doppler × range]`, Hann-windows the slow-time axis, and runs an
      inline DFT per range bin. Edge cases (empty channels, empty grid,
      zero-length range / Doppler) yield a correctly-shaped zero cube.
    - `pub fn rda_peak(cube) -> RdaPeak` — finds the global maximum cell
      and decodes the angle / Doppler axes back to physical units (az,
      el in degrees; Doppler in fractional units when `pri_s` is unity).
    - `pub fn rda_extract_angle_slice(cube, angle_idx) -> Option<&Vec<Vec<f32>>>` —
      borrows the angle slice without copying; returns `None` when the
      index is out of range.
    - `pub fn rda_to_rd_sum(cube) -> Vec<Vec<f32>>` — collapses the
      angle axis to a single 2-D range-Doppler map by summing power
      across angles. Output is `rd[doppler][range]`, non-negative by
      construction.
  - Internal helpers (private): `hann_window(n)`, `dft_in_place(buf)`
    (forward DFT, `X[k] = Σ x[n] · exp(-j 2π n k / N)`, matching the

## Notes / Risks / Follow-ups

- **Strict-open posture.** The cube is in linear power-domain `f32`,
  matching the existing `RangeDoppler` (2-D) convention used by every
  detector in `crates/echoforge-radar/src/detectors/`. The packet
  brief suggested a `Vec<Complex<f32>>` IQ layout, but adopting that
  would have forced every downstream detector to be rewritten in
  parallel (the 2-D `RangeDoppler` they consume is `Vec<Vec<f32>>`).
  Complex IQ is preserved end-to-end *inside* `build_rda_cube`
  (beamforming and the Doppler DFT both run on `Complex<f64>`); only
  the final cube cells are squared-magnitude. The strict-open posture
  here is: the cube *is* the canonical 3-D primitive, and the layout
  matches the 2-D primitive it generalises. A follow-up packet that
  needs complex cube cells (e.g. for Capon / MVDR adaptive
  beamforming applied at the cube stage) can add a sibling
  `RangeDopplerAngleIq` type without breaking this one.
- **Inline DFT, not rustfft.** The crate has `rustfft = "6"` in its
  `Cargo.toml`, but the Doppler axis is short (a few dozen bins) and
  is run per range bin per angle, so the O(N²) inline DFT is not the
  hot path and keeps the code trivially auditable. Swapping to rustfft
  would not change a single test result (the inline DFT matches the
  rustfft "forward" convention `X[k] = Σ x[n] · exp(-j 2π n k / N)`)
  but would introduce a chunking-dependent floating-point reduction
  order that complicates the byte-identical determinism guarantee.
- **Wavelength source.** `build_rda_cube` takes `carrier_hz` and
  passes it to `steering_vector`, which derives the wavelength via
  `lambda = c / carrier_hz`. The `pri_s` parameter is plumbed through
  for the Doppler-Hz decoding in `rda_peak`; the cube layout itself
  is not `fftshift`ed (bin 0 = DC, bin `N-1` = `(N-1)/(N·pri_s)` Hz)
  so consumers can apply their own shift convention if needed.
- **ULA only.** The current `steering_vector` helper steers a uniform
  linear array in azimuth. The `AngleGrid` exposes elevation slices
  so a 2-D (planar) array can be wired in later without an API
  change; for now elevation is carried through `RdaPeak` but does not
  perturb the ULA steering.
- **lib.rs untouched by this packet.** The `pub mod rda_cube;` line
  and the `pub use` re-export block were already present at the start
  of the slot, per the packet boundary that says "DO NOT edit lib.rs
  — the orchestrating Claude … will wire `pub mod rda_cube;` and
  re-exports centrally". I did not modify `lib.rs`.
- **Cargo.toml untouched.** No new dependencies added. The crate's
  pre-existing `num-complex = "0.4"` covers the complex-number type
  used here.
- **local coordination scratchpad untouched.** The parent coordinator will append a
  message on its own cadence.
- **Sibling modules byte-stable.** I did not touch `sim.rs`,
  `clutter.rs`, `rfi.rs`, `impairments.rs`, `micro_doppler_gen.rs`,
  `beamforming.rs`, `antenna.rs`, `chain.rs`, `cfar.rs`,
  `pulse_compression.rs`, `waveform.rs`, `backend.rs`,
  `tracking_fusion.rs`, or anything under `detectors/` or `fusion/`.
  The 62 pre-existing tests in those modules all continue to pass.
- **What this unblocks.** `baseline-detector-classifier-tracker` was
  blocked on the RDA cube primitive. With `build_rda_cube`,
  `rda_peak`, `rda_extract_angle_slice`, and `rda_to_rd_sum` now
