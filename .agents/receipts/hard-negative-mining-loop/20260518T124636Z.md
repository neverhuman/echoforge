## Scope

Builds the closed-loop hard-negative curriculum that local coordination scratchpad's Critical
Review section I called out as missing ("Hard-negative mining loop is the
four-card placeholder, not a loop").

- One iteration reads `model_eval_*.json` rollups from a campaign root's
  `qa/` dir.
- Per-class false-alarm counts are aggregated into `FailureCluster`s and
  filtered to those whose fp_rate exceeds a configurable threshold.
- Each cluster's base `ObjectClass` is looked up in the supplied airspace
  library and a perturbed variant entry is synthesized (widens
  kinematics, micro-motion, sensor-observable envelopes; bumps RCS upper
  bound; tags `mined_variant`; records `mined_provenance`).
- The cluster store + proposed variants + an iteration manifest are
  written under `outputs/hard-negative-runs/iteration-<N>/` for curator
  review.
- The loop deliberately stops at "proposed variants on disk". Applying
  variants to the live `configs/monte-carlo/airspace-objects-v1.json` is
  the responsibility of a follow-up `apply_variants` packet — humans
  remain in the loop. This packet adds the mining apparatus, not the
  appender.

## Notes

- The new crate has **zero** dependency on `echoforge-radar` or
  `echoforge-dataset`. It consumes the on-disk JSON shapes that the
  streaming runner emits, not the runner's Rust types. The shapes are
  re-declared in `types.rs` and round-trip via `serde_json::Value`
  containers (`extra` fields) for fields the loop doesn't manipulate, so
  upstream schema growth doesn't break this crate.
- Synthesizer widening policy: per-envelope multiplicative widening
  bounded by `WIDEN_MIN=1.05` and `WIDEN_MAX=1.40`, scaled by
  `(fp_rate - fp_threshold) * DEFAULT_WIDEN_GAIN`. Non-negative fields
  (RCS not included) are clamped at zero on the lower bound. RCS upper
  bound is bumped by a fixed `RCS_UPPER_BUMP_DB=2.5 dB` because dB is
  already a log scale and the linear multiplicative widening would
  understate the perturbation.
- `classification_prior` is intentionally NOT perturbed — that field
  shapes the dataset class balance and is a curator-controlled lever,
  not a mining-loop output.
- `mined_provenance` block in each variant's `extra` map records the
  base class id, the source cluster, the threshold, the widening factor,
  and the variant index, so curator review can trace why each envelope
  moved without re-running the loop.
- Iteration numbering: each iteration's variant ids embed the iteration
  number × 100 plus a per-cluster index, so iteration 0 emits
  `<base>-mined-v0..vK`, iteration 1 emits `-mined-v100..v100+K`, etc.
  This prevents id collisions across iterations even if the same base
  class is mined twice.

## Risks

- **Family-id vs object_family vocabulary mismatch.** The campaign
  runner's `false_alarm_by_hard_negative_family` keys are a hardcoded
  vocabulary (`infrastructure_glint`, `commercial_aircraft_corridor`,
  ...). The airspace library uses `object_family` slugs that overlap but
  do not coincide (`commercial_aircraft_corridor` matches;
  `infrastructure_glint` is grouped under
  `static_or_rotating_infrastructure` instead). My synthesizer matches by
  `object_family` first and falls back to direct `id` match; clusters
  with no matching base class are skipped (not erroring). A future
  packet should formalise a `family_aliases.toml` so curator can map
  campaign families to airspace families without code changes.
- **No FP rate denominator per family.** The streaming runner reports
  per-detector `negative_records` as a total (not per family), so my
  aggregator's `fp_rate = sum_fps / sum_negatives_across_detectors` is
  an approximation. It under-weights families that occupy a small
  fraction of the negative pool. For early iterations of the curriculum
  this is fine because we surface the highest-rate clusters first;
  later iterations should switch to a per-family denominator once the
  runner exposes one.
- **No automatic re-bench.** This packet does not run the dataset
  generator or the detectors. After a curator approves variants, the
  full close-the-loop iteration requires regenerating the dataset and
  re-running the streaming runner against it. That orchestration lives
  in a future packet (`mining-loop-orchestrator` or similar) — keeping
  the boundary here narrow per local coordination scratchpad scope rules.
- **`outputs/hard-negative-runs/`** is under the gitignored
  `outputs/` tree, so iteration artifacts are local-only. Curators who
  want to share proposals across machines should copy
  `iteration-<N>/proposed_variants.json` out of `outputs/` and into a
  reviewable PR or follow-up packet's `staging/` directory.
