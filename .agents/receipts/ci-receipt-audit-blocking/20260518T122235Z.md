# CI Receipt-Audit Blocking Receipt

- Timestamp: `20260518T122235Z`
- Packet: `ci-receipt-audit-blocking` (per `FUCKIT.md` roadmap, 2026-05-18)
- Scope: `.github/workflows/jankurai.yml` only.

## Why

The `receipt-audit` job in `.github/workflows/jankurai.yml` ran with
`continue-on-error: true`, making the receipt guard advisory only.
With 38 existing receipts all currently OK, the guard is ready to be
promoted to a blocking gate so future malformed receipts fail CI
instead of being absorbed silently.

## Files Changed

- `.github/workflows/jankurai.yml`
  - Flipped the `receipt-audit` job's `continue-on-error: true` to
    `continue-on-error: false`. No other changes to the step body,
    runner, or invocation: the job still runs `node tools/receipt_guard.mjs --all`.
  - The `bootstrap` and `vendor-scrub` jobs are untouched; only the
    `receipt-audit` job was advisory and has been promoted.

## Scope

- ONLY `.github/workflows/jankurai.yml` was edited.
- `Justfile` was not modified: the `receipts` recipe (`node tools/receipt_guard.mjs --all`)
  already exists at line 62-63 and matches the pattern used by the
  other `node`-based recipes (`vendor-scrub`, `banlist-audit`), which
  intentionally invoke `node` directly rather than via `rtk`. Adding
  an `rtk` prefix here would be inconsistent with sibling recipes, so
  the existing recipe was left alone.
- No receipts were touched, rewritten, or backfilled.

## Commands

- `rtk node tools/receipt_guard.mjs --all` -> 38 receipt(s), 0 failing
  (verified BEFORE flipping the CI gate, so the promotion does not

- `rtk node tools/vendor_scrub.mjs` -> 231 files scanned, 17 real

- `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/jankurai.yml'))"`

  PyYAML used as the substitute structural validator).
- `rtk just --list` -> shows the existing `receipts` recipe is wired.

## Results

- The `receipt-audit` job is now blocking on `main`, on PRs, and on
  manual `workflow_dispatch`. A malformed receipt will fail CI rather
  than emit a yellow advisory annotation.
- All 38 currently-tracked receipts pass the guard, so the promotion
  is safe to land immediately and does not require any backfill.
- The diff applied to `.github/workflows/jankurai.yml` is a single
  one-character semantic flip (`true` -> `false`) on the
  `receipt-audit` job's `continue-on-error` key.

## Validation

- Before flipping: `node tools/receipt_guard.mjs --all` -> 38 OK,
  0 fail.
- After flipping: workflow YAML structure preserved (Python
  `yaml.safe_load` round-trip clean).
- Vendor scrub still green: 0 banlist hits in tracked files.

## Notes

- The decision to leave `Justfile` alone is deliberate: the
  `receipts` recipe already exists, and forcing an `rtk` prefix on a
  `node` invocation would diverge from the existing `vendor-scrub`
  and `banlist-audit` recipes in the same file. If the project later
  decides every `node` invocation in the Justfile should be wrapped
  in `rtk`, all three recipes should be updated together in a
  dedicated packet.
- yamllint is not available on the local toolchain; Python's PyYAML
  was used as a structural sanity check. Consider adding yamllint
  to the dev toolchain or the CI image so future workflow edits get
  a stricter lint than `yaml.safe_load`.

## Risks

- Risk surface is small: only CI gating semantics change. No script,
  recipe, or runtime code was touched. The single-line change can be
  reverted by flipping the boolean back if the gate turns out to be
  too strict in practice.
- If a future malformed receipt lands, CI will now block the PR
  instead of warning. That is the intended behavior of this packet.

## Follow-ups

- Consider adding `yamllint` to `Justfile` (e.g. `just lint-ci`) and
  to the `vendor-scrub` job so workflow YAML errors fail fast.
- Consider mirroring the receipt guard into a lefthook pre-commit
  hook so authors get feedback before pushing.
- The other `continue-on-error: true` job (`bootstrap`, line 13) is
  still advisory; promote when the curator decides scaffold
