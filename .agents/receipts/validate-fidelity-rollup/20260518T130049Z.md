# validate-fidelity-rollup — surface fidelity-class (F0-F5) reporting in echoforge-validate

- Timestamp: `20260518T130049Z`
- Packet: `validate-fidelity-rollup` (per `FUCKIT.md`)
- Scope: `crates/echoforge-validate/src/fidelity_rollup.rs` (NEW), `crates/echoforge-validate/src/lib.rs` (additive)

## Why

The `fidelity-class-field` packet (wave 2,
`.agents/receipts/fidelity-class-field/20260518T123632Z.md`) added the
optional `fidelity_class: Option<String>` field to
`echoforge_core::ValidationInfo` so producers can declare a
method-ceiling on the F0..F5 axis independently of the V0..V5
evidence-tier. That packet intentionally left the validate crate
untouched — it noted in its Notes that "[w]hen a future packet wants to
surface fidelity alongside the validate report, the natural extension
point is to read `bundle.manifest.validation.fidelity_class`" and that
read-path follow-up is what this packet lands.

This packet wires the field into reporting helpers so downstream
consumers can (a) aggregate fidelity-class distribution across a set of
artifacts and (b) assert a minimum fidelity floor on a single artifact.
The V0/V1/V2 promotion gate in `crates/echoforge-validate/src/report.rs`
remains byte-identical and does NOT read `fidelity_class` (per
`docs/validation-tiers.md` §"Promotion-gate behaviour (unchanged)").

## Files Changed

- `crates/echoforge-validate/src/fidelity_rollup.rs` — NEW. Adds:
  - `parse_fidelity_class(s: &str) -> Option<u8>` — strict parse of
    `"F0".."F5"` to `0..=5`. Rejects `"F6"`, `"f2"`, `"F2 "`, `""`,
    `"V2"`, `"F10"`, etc. so the rollup never silently coerces drifted
    labels.
  - `FidelityRollup { artifact_count, with_fidelity_class,
    without_fidelity_class, by_fidelity: BTreeMap<String, usize>,
    by_tier_x_fidelity: BTreeMap<(String, String), usize> }` —
    derives `Default, Serialize, Deserialize, PartialEq, Eq` so callers
    can round-trip the rollup through JSON / YAML deterministically
    (`BTreeMap` keys give stable ordering).
  - `rollup_validation_envelopes(envelopes: &[&ValidationInfo]) ->
    FidelityRollup` — single-pass aggregator. Envelopes without
    `fidelity_class` are bucketed into `without_fidelity_class` and
    excluded from the (tier x fidelity) cross-axis (the pair key would
    otherwise be ambiguous). Unknown labels (e.g. `"F9"`) are passed
    through verbatim so producer drift surfaces.
  - `FidelityFloor { min_fidelity: String }` plus `FidelityFloor::new`
    convenience constructor.
  - `FidelityFloorError` enum (via `thiserror`) with four variants:
    `Missing { floor }`, `UnparseableEnvelope { value }`,
    `UnparseableFloor { value }`, `Below { envelope, floor, got,
    required }`.
  - `assert_fidelity_floor(envelope: &ValidationInfo, floor:
    &FidelityFloor) -> Result<(), FidelityFloorError>` — parses both
    sides, returns `Err` on missing / unparseable / below-floor.
  - 11 unit tests in `#[cfg(test)] mod tests` (see Results).
- `crates/echoforge-validate/src/lib.rs` — additive: added
  `pub mod fidelity_rollup;` and a `pub use
  fidelity_rollup::{...}` re-export block. Preserved the concurrent
  `validation-tier-v3` packet's `pub mod tier_v3;` (it landed first;
  both modules sit adjacent in alphabetical order). No existing module
  declaration or re-export was touched.
- `.agents/receipts/validate-fidelity-rollup/20260518T130049Z.md` —
  this receipt.

Scope: additive module + lib.rs re-exports. No existing struct, no
existing function, no existing test changes; `ValidationInfo` itself is
sealed for this packet (`crates/echoforge-core/src/models.rs` untouched

## Notes / Risks / Follow-ups

- **`fidelity_class` does NOT enter the V0/V1/V2 promotion gate.** Per
  `docs/validation-tiers.md` §"Promotion-gate behaviour (unchanged)",
  `report::promotion_gate` continues to compute purely from
  `ValidateChecks`. This packet adds a parallel reporting + gate
  surface, not a modification to the canonical V-tier rule.
  Per-artifact `assert_fidelity_floor` is opt-in; a producer that
  wants F-floor enforcement at promotion time wires it explicitly.
- **Concurrent `validation-tier-v3` packet co-landing.** That packet
  added `pub mod tier_v3;` to `lib.rs` (visible in the in-tree state
  when this packet's edits were applied). The two modules sit adjacent
  in the module list; both packets re-export their symbols in the
  `pub use ...` block without conflict. No coordination edits were
  needed beyond preserving `tier_v3`'s line when editing `lib.rs`.
- **`BTreeMap` over `HashMap` for determinism.** The rollup uses
  `BTreeMap` keys for `by_fidelity` and `by_tier_x_fidelity` so JSON
  serialization is byte-stable (sorted keys); a downstream consumer
  can hash the serialized rollup without ordering drift.
- **Unknown labels passed through verbatim.** `rollup_validation_envelopes`
  intentionally does NOT filter to F0..F5 on the by-fidelity map;
  if a producer emits `"F9"` (drift), the count surfaces in the
  rollup so it is auditable. The strict `parse_fidelity_class` check
  only gates the floor enforcement path (`assert_fidelity_floor`).
- **No external deps added.** `thiserror`, `serde`, `serde_json`,
  `echoforge-core` were already declared in `crates/echoforge-validate/Cargo.toml`.
- **`ValidationInfo` untouched.** Per packet boundary,
  `crates/echoforge-core/src/models.rs` is not modified. The
  `fidelity_class: Option<String>` field added by `fidelity-class-field`
  is consumed by reference only.
- **Out of scope (follow-ups).** (a) CLI surfacing of the rollup
  alongside `ValidateReport` (would attach to `ValidateReport.notes`
  or a new optional field — `report.rs` is sealed for this packet).
  (b) Coherence checks across `tier` x `fidelity` (e.g. flag
  `tier: V5-measured` + `fidelity_class: F0`); per
  `fidelity-class-field` Notes that lives in a separate validation
  rule, not in this reporting module.
- **Receipt format conformance.** Filename matches
  `^\d{8}T\d{6}Z?(?:-\d{4})?\.md$`; H1 present; required H2 sections
  ("Files Changed", "Commands", "Results / Validation", "Notes /
  Risks / Follow-ups") present; bullets under Files Changed; multiple
