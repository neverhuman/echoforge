# fidelity-class-field — separate method-ceiling (F0-F5) from evidence-tier (V0-V5)

## Files Changed

- `schemas/common.schema.json` — additive bump to `$defs/validation`.
  Added optional `fidelity_class` property: `string` enum
  `["F0","F1","F2","F3","F4","F5"]` with a description that pins the
  semantics (F0=analytic-prior, F1=primitive-decomposed,
  F2=production-SBR, F3=cross-solver-bridged, F4=measured-anchored,
  F5=lawful-measured-validated). NOT added to `required`; the existing
  required set (`tier`, `status`, `uncertainty_score`, `checks`) is
  untouched. `additionalProperties: false` already in place — the new
  key joins the closed property set additively.
- `crates/echoforge-core/src/models.rs` — added
  `pub fidelity_class: Option<String>` to `ValidationInfo` with
  `#[serde(default, skip_serializing_if = "Option::is_none")]` so
  existing serialized payloads (and the contract-smoke golden SHA-256
  hashes) remain byte-stable when the field is absent. The Rust struct
  accepts any `Option<String>` for forward compatibility; the JSON
  Schema is the enforcement surface for the F0..F5 enum. Inline
  comments cross-reference the local coordination archive cross-tip resolution.
- `crates/echoforge-core/src/lib.rs` — added `fidelity_class: None` to
  the `#[cfg(test)] mod tests::sample_common` literal so the in-crate
  test compiles after the struct bump.
- `crates/echoforge-core/tests/common/samples.rs` — added
  `fidelity_class: None` to the canonical `validation_info()` builder.
  Required because the struct literal would otherwise fail to compile;
  the absence on the wire keeps the golden SHA-256 stable (no payload
  bytes change).
- `crates/echoforge-core/tests/contracts.rs` — added `fidelity_class:
  None` to the `ValidationInfo` literal in
  `object_card_finalizes_with_schema_version_and_fingerprint` for the
  same reason.
- `crates/echoforge-core/tests/fidelity_class.rs` — NEW integration
  test (5 tests). Pins: (a) `ValidationInfo` without `fidelity_class`
  serializes/deserializes cleanly and stays schema-valid; (b) with
  `fidelity_class: "F2"` round-trips cleanly and stays schema-valid;
  (c) every documented F0..F5 enum value validates; (d) invalid enum
  values (`"F6"`, `"f2"`, `"F2 "`, `""`, `"V2"`, etc.) are rejected by
  the schema; (e) every cross-axis combination of `tier`
  (unvalidated..measured) × `fidelity_class` (F0..F5) is schema-valid,
  documenting that the two axes are independent.
- `crates/echoforge-sig/tests/bundle_round_trip.rs` — added
  `fidelity_class: None` to the `sample_manifest()` builder's
  `ValidationInfo` literal so the sig crate's test build still
  compiles after the additive struct bump. Trivial mechanical
  one-liner; the wire format is unchanged (skip-serializing keeps the
  golden bundle bytes stable).
- `docs/validation-tiers.md` — appended a new section "Fidelity class
  (F0-F5) - the method-ceiling axis". Explains the two-axis model
  (`tier` = evidence accumulation, `fidelity_class` = method ceiling),
  gives the F0..F5 ladder table, walks four cross-axis examples
  (V1+F2, V0+F0, V2+F4, V5+F5), confirms the V-tier promotion gate is
  unchanged, and documents the additive Schema + Rust shape.
- `.agents/receipts/fidelity-class-field/20260518T123632Z.md` — this
  receipt.

Scope: schema-only additive bump plus minimum Rust binding wiring plus
documentation. No existing required field, enum value, or
serialization format is changed. No promotion-gate logic in
`echoforge-validate` is touched (see Notes).

## Notes / Risks / Follow-ups

- **Schema bump is additive only.** `$defs/validation.required` stays
  `["tier","status","uncertainty_score","checks"]`. All existing
  fixtures (the 12 `tests/schemas/*.sample.json` documents,
  `object-packs/public-proxy-v1/material_card.yaml`, every Rust-emitted
  canonical payload) continue to validate unchanged. `schema_version`
  remains pinned at `1.0.0`.
- **`echoforge-validate` not modified.** Per plan step 5, I checked
  `crates/echoforge-validate/src/report.rs` for `ValidationTier` /
  `ValidationInfo` references; the validate crate defines its own
  `TierAchieved {V0,V1,V2}` and `ValidateChecks` structs and does
  **not** import `echoforge_core::ValidationInfo`, so no read-path
  changes are needed. The V0/V1/V2 promotion gate logic stays
  byte-identical. When a future packet wants to surface fidelity
  alongside the validate report, the natural extension point is to
  read `bundle.manifest.validation.fidelity_class` in `cli::run` and
  attach it to `ValidateReport.notes` (or a new optional field) —
  out of scope here.
- **Workspace-wide `cargo test --workspace` (`rtk just fast`) cannot
  run in the current repo snapshot** because
  `crates/echoforge-radar/src/lib.rs` declares `mod backend;` but
  `crates/echoforge-radar/src/backend.rs` is currently deleted as part
  of Codex's in-flight `gpu-doctor-real-checks` packet (status
  `in-progress:codex` per `local coordination scratchpad`). Same goes for
  `crates/echoforge-dataset/{src/monte_carlo.rs, src/campaign.rs,
  Cargo.toml}` which are Codex's `campaign-gpu-readiness-gate`
  in-flight zone. **Pre-existing broken state, not caused by this
  packet.** All crates that DO build cleanly (core, sig, validate,
  world, contracts-smoke) pass.
- **Codex's two in-flight files will need `fidelity_class: None`
  added on rebase.** `crates/echoforge-dataset/src/monte_carlo.rs`
  (the `validation_info(uncertainty_score)` helper around line 1221)
  and `crates/echoforge-dataset/src/campaign.rs` (the
  `validation: ValidationInfo { ... }` literal around line 2018) each
  construct a `ValidationInfo` via struct literal; once Codex's two
  packets land (`gpu-doctor-real-checks` and
  `campaign-gpu-readiness-gate`), one trivial line — `fidelity_class:
  None,` — must be appended to each literal so the dataset crate
  builds. **This packet intentionally did NOT touch those files**
  per the local coordination scratchpad `DO NOT touch` boundary for Codex's active edit
  zone; the merge cost is one line per literal. The receipt for
  whichever Codex packet lands second should mention the addition.
- **`tests/schemas/*.sample.json` fixtures were intentionally not
  updated.** All 12 existing fixtures omit `fidelity_class` and
  continue to validate (per `schemas_and_samples_validate`). A
  follow-up packet may extend the material_card and validation_report
  sample fixtures with an explicit `fidelity_class: "F2"` (or
  similar) to exercise the field path in fixture-driven validation.
  Out of scope for the minimal additive bump.
- **Strongly-typed enum vs `Option<String>`.** The packet plan
  offered the choice of "Option<String> (or strongly-typed enum)".
  I chose `Option<String>` for symmetry with the existing
  `ValidationInfo.tier: String` (also a string, also schema-enforced
  enum), and to keep the Rust struct forward-compatible if the F0..F5
  vocabulary is extended (e.g. F6 lawful-measured-cross-checked).
  Enum enforcement lives in the schema. A future packet that wants a
  strongly-typed `FidelityClass` Rust enum can add `impl
  FromStr/Display` on top of the string field without bumping the
  schema or breaking serialization.
- **Cross-axis combinations are not promotion-gated.** The schema
  permits all 5 × 6 = 30 combinations of `tier` × `fidelity_class`
  (see the `fidelity_class_is_independent_from_tier` test); no
  business logic restricts which combinations are sensible. If
  downstream consumers want to flag "incoherent" combinations (e.g.
  `tier: V5-measured` + `fidelity_class: F0-analytic-prior`), that
  belongs in a separate validation rule, not in the schema enum
  itself.
