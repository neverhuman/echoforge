## Scope

- Build a Node-only static-HTML renderer for `validation_report.json`
  documents (per `schemas/validation_report.schema.json`). Single-file
  output, inline CSS, no JS, no external assets, deterministic bytes
  across reruns. Wired through `rtk` via a new Justfile recipe.
- Strict-open posture: the rendered HTML mirrors what the JSON
  asserts. No synthesized "validated" / "ground truth" badges; status
  badges, tier and fidelity_class labels are echoed verbatim from the
  input envelope. Footer literally says "public-proxy validation
  dossier — strict-open EchoForge".
- The renderer is purely additive: it does not touch any schema, Rust
  crate, agent config, .github file, or any pre-existing tool.

## Files Changed

- `tools/render_validation_dossier.mjs` (new, Node ESM)
  - Single-file HTML5 renderer. Accepts `<input.json>` and an optional
    `--out <path>`. Default output is `<input>.html` next to the
    input. Validates that the required top-level fields are present
    (`id`, `kind`, `subject_kind`, `subject_id`, `overall_status`,
    `checks`, `provenance`, `license`) plus a tier (accepts both
    canonical `validation.tier` and the older top-level `tier` shape
    used by some fixtures), checks `kind == "validation_report"`,
    asserts `checks` is non-empty, and gates `overall_status` to
    pass|warn|fail. Renders header (subject identity, generated_at,
    fingerprint), status badge, tier + optional fidelity_class badges,
    uncertainty gauge (color-coded low/mid/high band by `[0, 1]`
    score), provenance + license sections, per-check table, and the
    strict-open footer. CSS is inline in a `<style>` block; no
    JavaScript; no external assets. Exit codes: 0 success / 1
    validation-or-IO / 3 usage. Determinism: every loop iterates an
    input array in declared order or a fixed key list, no Map
    iteration on undefined order, no timestamps in output.
- `tools/test_render_validation_dossier.mjs` (new, Node ESM)
  - Std-lib-only test driver, 7 cases / 26 sub-checks: (1) minimal
    valid report renders subject_id, status badge, and all check
    names; (2) `tier: V2` + `fidelity_class: F2` both badges appear
    with their respective CSS classes; (3) input missing a required
    field exits non-zero and stderr names the missing field; (4)
    output is byte-identical across two reruns of the same input
    (the determinism property the repro-bytes lane cares about); (5)
    default `--out` is `<input>.html` next to the input; (6)
    `kind != "validation_report"` is rejected and stderr says so;
    (7) zero positional args exits with usage code 3.
- `Justfile`
  - Added `render-validation-dossier` recipe:
    `rtk node tools/render_validation_dossier.mjs {{args}}`.

## Validation

- The renderer is intentionally output-faithful: it never invents
  status, never collapses warn into pass, never hides a check. A
  missing `validation.uncertainty_score` renders as a muted "no
  uncertainty_score in validation envelope" gauge instead of a
  default-0.0 bar that could read as "validated".
- `fidelity_class` (F0–F5) and `tier` (V0–V5 / string-alias) render
  as two distinct badges with different colors, reinforcing the
  doc-level invariant from `docs/validation-tiers.md` that evidence
  and method-ceiling are independent axes.
- Determinism property: the test asserts byte-equality across two
  invocations on the same input. If a future change adds a timestamp,
  randomness, or undefined-order iteration, test4 will fail before the
  bytes drift downstream into any repro-bytes lane.
- No npm dependencies installed; only Node std (`fs`, `path`,
  `child_process`, `os`).

## Notes / Risks / Follow-ups

- The schema places `tier` inside the `validation` envelope. The
  prompt also lists `tier` as a required top-level field. The
  renderer accepts either shape — `validation.tier` (canonical) or
  top-level `tier` (older fixtures like
  `tests/science/fixtures/bundles/v1_pass/qa/validation_report.json`)
  — and only fails validation if neither is present. This keeps the
  tool useful against both fixture shapes in the tree today.
- The `metric` column in the checks table renders whatever value
  `check.metric` holds (as JSON). The shared `validation_check`
  schema does not currently define a `metric` field, so for
  schema-conformant inputs that column is always em-dash. The
  column is preserved for forward compatibility with future
  check-level metric extensions; removing it later is a no-op for
  conformant inputs.
- The HTML uses a `prefers-color-scheme: dark` media query and CSS
  custom properties so the dossier reads cleanly in both light and
  dark browsers. This is style-only and does not affect determinism.
- Scope guardrails: I did **not** touch `schemas/`, any Rust crate,
  any existing tool, `agent/`, `.github/`, or `docker/`. The only
  modifications outside the two new tools and this receipt are the
  Justfile (recipe addition).
