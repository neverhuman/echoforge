I studied all seven proposal files in the archive: `tip1.txt` through `tip7.txt`. The strongest raw proposal is **Tip6**, with **Tip5** and **Tip7** close behind. The best final system should combine Tip6’s artifact standard and validation discipline, Tip5’s native radar-kernel engineering, Tip7’s validation/split policy and product clarity, Tip4’s physically layered hard-negative strategy, and Tip1’s broad end-to-end workflow.

I also verified several important stack assumptions against current public documentation. **SagittaSBR** is a strong candidate for a core GPU RCS engine because it is an open C++/CUDA project for monostatic far-field RCS using SBR with GO/PO methods. **Sionna RT** is valuable for radio-propagation and scene ray tracing, but it should not be treated as a target-RCS solver. **RadarSimPy** should remain optional/plugin-only because its own docs distinguish free and licensed modes, and building from source depends on access to non-public `radarsimcpp` sources. For validation, open solvers such as openEMS, SCUFF-EM, Bempp, and Palace are credible cross-check tools, each with different numerical tradeoffs. ([GitHub][1])

For storage, orchestration, and GPU execution, the proposals’ repeated use of Zarr, Ray, Docker GPU support, and the NVIDIA Container Toolkit is well aligned with current public documentation. Zarr is appropriate for chunked compressed N-dimensional arrays, Ray is appropriate for distributed Python tasks/actors including GPU-aware resource scheduling, and Docker Compose/NVIDIA tooling support GPU-enabled containers. Stone Soup is also a good tracking-benchmark dependency because it is specifically designed for developing and testing tracking/state-estimation algorithms. ([Zarr][2])

# 5. Product definition

**EchoForge** is a GPU-first synthetic radar and RF-sensing workbench for creating, validating, and benchmarking believable radar signatures, clutter worlds, false positives, and tracking datasets.

It is not a “make a pretty RCS plot” tool. It is a full pipeline:

```text
Object hypothesis
  → geometry variants
  → material uncertainty
  → mesh QA
  → RCS / scattering products
  → dynamic signature synthesis
  → scene + propagation effects
  → radar signal chain
  → detection products
  → tracking products
  → benchmark dataset
  → validation report
```

The design principle is:

> Every generated artifact must carry its source assumptions, solver path, uncertainty, validation tier, and benchmark split lineage.

That is what makes the system credible to serious radar reviewers.

---

# 6. Non-negotiable guardrails

EchoForge should be powerful, but it must be honest.

## Allowed core goals

EchoForge should support:

* public-proxy UAV and aircraft-like object classes,
* low-altitude and near-ground scene conditions,
* clutter-heavy environments,
* hard-negative false-alarm generation,
* generic radar waveform/sensor archetypes,
* synthetic dataset generation,
* object and scenario uncertainty modeling,
* solver comparison,
* validation grading,
* tracking benchmark generation,
* reproducible GPU batch simulation.

## Hard non-goals

EchoForge should not include:

* exact proprietary radar clones,
* classified or restricted parameters,
* claims of exact real hostile-platform signatures without lawful measured data,
* weapon engagement workflows,
* evasion optimization,
* jamming/countermeasure defeat recipes,
* operational detection-range claims,
* banned vendor references in docs, code, configs, comments, examples, or tests.

The target pack can include **public-proxy low-altitude UAV archetypes inspired by open-source reporting**, but the system should label them as **proxy families with uncertainty envelopes**, not exact replicas.

# 8. Core subsystems

## 8.1 Asset Forge

Asset Forge manages objects before they become signatures.

### Responsibilities

* Import CAD/mesh assets.
* Normalize units and coordinate frames.
* Repair meshes.
* Generate geometry variants.
* Assign material cards.
* Attach public-source/provenance cards.
* Define dynamic components.
* Produce mesh QA reports.

### Inputs

Supported initial formats:

* `.obj`
* `.stl`
* `.ply`
* `.glb`
* `.gltf`
* `.step` through optional converter container
* procedural primitives for analytic tests

### Output artifact

```text
AssetCard
  object_id
  object_family
  proxy_status
  source_dossier
  geometry_manifest
  material_manifest
  dynamic_manifest
  uncertainty_manifest
  qa_report
```

### Object ID policy

Do not use exact real platform names in primary object IDs. Use neutral archetypes:

```yaml
object_id: uav.public_proxy.medium_delta_low_altitude_v1
object_family: low_altitude_uav_proxy
proxy_status: public_proxy_uncertainty_bounded
aliases:
  policy: source_dossier_only
```

The alias system can store public-source associations in a controlled source dossier, but dataset labels should remain neutral.

### Mesh QA checks

Each imported asset must pass:

* unit normalization,
* watertightness report,
* manifoldness report,
* triangle count range,
* degenerate face check,
* normal orientation check,
* bounding box sanity check,
* material coverage check,
* dynamic-part attachment check,
* solver compatibility check.

Mesh QA should not silently repair everything. It should classify repairs:

```text
PASS        usable as-is
REPAIRED    usable, but geometry changed
WARN        usable for low-confidence proxy only
FAIL        cannot enter production simulation
```

## 8.2 Material Forge

Material modeling must be explicit. Every signature should say what material assumptions were used.

### Material card fields

```yaml
material_id: composite.generic_low_loss_v1
category: composite
frequency_model:
  type: tabulated_or_parametric
  valid_band: generic_band_label
electrical_properties:
  permittivity:
    distribution: bounded_uniform
    value_range: [redacted_for_public_proxy, redacted_for_public_proxy]
  conductivity:
    distribution: log_uniform
    value_range: [redacted_for_public_proxy, redacted_for_public_proxy]
surface:
  roughness_model: bounded_random_field
  coating: unknown_public_proxy
confidence:
  grade: bronze
  reason: "Public-proxy assumption; no measured coupon data."
provenance:
  source_type: public_proxy_estimate
  review_status: unvalidated
```

Avoid hard-coding sensitive or over-specific real-platform material values. Use distributions and confidence labels.

### Material confidence grades

| Grade    | Meaning                                                                |
| -------- | ---------------------------------------------------------------------- |
| Bronze   | Public-proxy assumption; useful for broad simulation only.             |
| Silver   | Public literature or engineering estimate with documented uncertainty. |
| Gold     | Calibrated against lawful measured component or coupon data.           |
| Platinum | Independently reviewed measured-data-backed model.                     |

## 8.3 RCS Forge

RCS Forge produces angle/frequency/polarization-dependent scattering artifacts.

### Solver strategy

Use a **strict-open default**:

1. **Production GPU solver:** SagittaSBR-style adapter for large sweeps and high throughput.
2. **Analytic solver:** built-in sphere, plate, dihedral/trihedral sanity cases.
3. **Open full-wave spot validators:** openEMS, SCUFF-EM, Bempp, Palace depending on geometry and frequency regime.
4. **Optional plugins:** isolated containers for any restricted, commercial, or license-conditional tools.

SagittaSBR is suitable as the production candidate because it is public C++/CUDA software for monostatic far-field RCS using SBR with GO/PO methods. Full-wave validators are not used for every production sweep; they are used for smaller canonical objects, reduced-frequency cases, and spot checks. ([GitHub][1])

### Why not make RadarSimPy the core?

RadarSimPy can be useful as an optional comparison or educational plugin, but it should not be the foundation. Its docs distinguish free and licensed operating modes, and its build-from-source path depends on access to `radarsimcpp` source. That is not acceptable for EchoForge’s core CI, open examples, or default reproducibility. ([Radar Sim X][3])

### RCS output must never be scalar-only

Minimum RCS cube axes:

```text
frequency
azimuth
elevation
polarization_tx
polarization_rx
variant
time_phase optional
```

Recommended tensor names:

```text
rcs_dbsm[freq, az, el, pol_tx, pol_rx, variant]
phase_rad[freq, az, el, pol_tx, pol_rx, variant]
confidence[freq, az, el, variant]
validity_mask[freq, az, el, variant]
```

### Solver adapter contract

```python
from typing import Protocol, Mapping, Any
from pathlib import Path

class SolverAdapter(Protocol):
    name: str
    version: str
    license_class: str  # "core_open", "optional_open", "restricted_plugin"

    def validate_inputs(
        self,
        asset_card: Mapping[str, Any],
        sweep_card: Mapping[str, Any],
    ) -> Mapping[str, Any]:
        """Return pass/warn/fail checks before scheduling."""

    def estimate_cost(
        self,
        asset_card: Mapping[str, Any],
        sweep_card: Mapping[str, Any],
    ) -> Mapping[str, Any]:
        """Return expected GPU memory, runtime class, and chunk plan."""

    def run(
        self,
        asset_path: Path,
        material_card_path: Path,
        sweep_card_path: Path,
        output_dir: Path,
    ) -> Path:
        """Produce an EchoSig-compatible artifact."""

    def summarize_quality(
        self,
        output_dir: Path,
    ) -> Mapping[str, Any]:
        """Return solver warnings, convergence notes, and validity masks."""
```

## 8.4 EchoSig artifact standard

EchoSig is the central artifact format. It should be a directory, not a single loose file.

```text
echosig/
  manifest.yaml
  source_card.yaml
  geometry_card.yaml
  material_card.yaml
  solver_card.yaml
  sweep_card.yaml
  tensors.zarr/
  qa_report.json
  validation_report.json
  preview/
    rcs_heatmap.png
    polar_summary.png
    aspect_slices.png
  logs/
    solver.log
    environment.json
```

Zarr is a good fit because it is designed for chunked compressed N-dimensional arrays, which is exactly what large RCS and radar tensors need. ([Zarr][2])

### EchoSig manifest

```yaml
schema: echoforge.echosig.v1
artifact_id: echosig_2026_000001
object_id: uav.public_proxy.medium_delta_low_altitude_v1
object_family: low_altitude_uav_proxy

proxy_status:
  type: public_proxy
  exact_real_platform_claim: false
  measured_signature_backed: false
  uncertainty_required: true

coordinate_frame:
  convention: ENU_body_aligned_v1
  units: SI
  angle_units: deg

sweep:
  frequency_axis_id: freq_generic_v1
  azimuth_grid: az_0_360_regular
  elevation_grid: el_low_to_high_regular
  polarization_basis: linear_hv

solver:
  primary: sagitta_sbr_adapter
  validation:
    analytic_cases_passed: true
    full_wave_spot_check: optional_or_completed
  license_class: core_open

data:
  tensors: tensors.zarr
  variables:
    - rcs_dbsm
    - phase_rad
    - confidence
    - validity_mask

credibility:
  grade: bronze
  reason: public_proxy_geometry_and_material_uncertainty
  allowed_uses:
    - algorithm_stress_testing
    - false_alarm_benchmarking
    - qualitative_signature_exploration
  disallowed_claims:
    - exact_real_platform_signature
    - operational_detection_range_claim

provenance:
  created_by: echoforge
  git_commit: ${GIT_COMMIT}
  container_digest: ${CONTAINER_DIGEST}
  generated_at_utc: ${TIMESTAMP}
```

## 8.5 Dynamic Signature Forge

Static RCS is insufficient for low-altitude UAV-style scenes. EchoForge needs dynamic signatures.

### Dynamic object model

```yaml
dynamic_manifest:
  rigid_body:
    pose_source: trajectory_generator
    attitude_model: stochastic_low_altitude_attitude_v1
  rotating_components:
    - component_id: propulsor_0
      geometry_ref: mesh_parts/propulsor_0.obj
      rpm_model: bounded_distribution
      phase_sampling: regular_or_random
      confidence: bronze
    - component_id: propulsor_1
      geometry_ref: mesh_parts/propulsor_1.obj
      rpm_model: bounded_distribution
      phase_sampling: regular_or_random
      confidence: bronze
  articulation:
    enabled: false
```

### Dynamic outputs

```text

```

### Minimum dynamic tests

1. Static sphere has no micro-Doppler.
2. Rotating idealized blade produces symmetric Doppler sidebands.
3. Increasing rotation rate increases sideband spread.
4. Dynamic artifact remains deterministic under fixed seed.
5. Validity mask reflects undersampled rotation/phase cases.

### Hard-negative philosophy

Hard negatives should not be random junk. They should be plausible returns that create realistic false-alarm pressure.

Hard-negative families:

| Family                        | Why it matters                                                     |
| ----------------------------- | ------------------------------------------------------------------ |
| Birds / flocks                | Small moving targets with biological micro-Doppler-like structure. |
| Ground vehicles               | Low-altitude mover confusion and road-correlated motion.           |
| Wind turbines                 | Strong rotating signatures and periodic Doppler.                   |
| Towers / masts                | Bright static reflectors and sidelobe contamination.               |
| Buildings                     | Specular glints and multipath.                                     |
| Vegetation                    | Wind-driven clutter and nonrigid motion.                           |
| Terrain ridges                | grazing-angle ground clutter and shadowing.                        |
| Small boats / coastal objects | moving clutter in coastal scenes.                                  |
| Agricultural equipment        | large intermittent movers with odd aspect signatures.              |
| Unknown movers                | catch-all for open-set evaluation.                                 |

### Split-safe benchmark policy

The system must avoid train/test leakage.

```text
Object split:
  no identical object geometry across train/test

Variant split:
  no same mesh with only material perturbation across train/test unless explicitly marked

Scene split:
  terrain seeds and clutter seeds separated

Trajectory split:
  trajectory seed families separated

Hard-negative split:
  confuser object families balanced but seed-separated

Sensor split:
  optional domain shift between train and test archetypes

Validation split:
  measured/calibration data never used for training unless explicitly authorized
```

## 8.8 Propagation and scene ray tools

Sionna RT should be used for scene-level radio propagation, not as a replacement for target scattering/RCS. It is a differentiable radio-propagation ray tracer and can help model multipath, scene interactions, and communications/radio-channel effects in complex environments. ([NV Labs][5])

### Correct use

Use it for:

* propagation paths,
* multipath,
* scene interaction,
* environment ray effects,
* differentiable scene studies.

Do not use it as:

* the primary target RCS engine,
* a full EM solver for arbitrary UAV materials,
* a substitute for RCS validation.

## 8.9 Validation Forge

Validation Forge is the credibility engine.

### Validation ladder

| Tier | Name                         | Meaning                                                                                 |
| ---: | ---------------------------- | --------------------------------------------------------------------------------------- |
|   V0 | Schema-valid                 | Artifact is well-formed but not physically validated.                                   |
|   V1 | Analytic sanity              | Passes known canonical cases: sphere, plate, dihedral/trihedral, point target.          |
|   V2 | Solver consistency           | Production solver agrees with one or more independent open solvers on simplified cases. |
|   V3 | Perturbation stability       | Geometry/material/mesh perturbations behave plausibly and uncertainty is bounded.       |
|   V4 | Public benchmark consistency | Consistent with public literature ranges/qualitative behavior where available.          |
|   V5 | Measured-data calibrated     | Calibrated against lawful measured data with documented setup.                          |

Most public-proxy target artifacts should start at **V1–V3**. Only lawful measured-data-backed artifacts can be V5.

### Required validation tests

#### Analytic RCS tests

* Perfect conducting sphere trend test.
* Flat plate aspect response.
* Dihedral/trihedral strong-return sanity.
* Point scatterer range/Doppler placement.
* Polarization-basis consistency.

#### Radar-chain tests

* Single stationary point target appears in correct range bin.
* Moving point target appears in correct Doppler bin.
* Two point targets resolve according to configured resolution.
* Noise-only scene produces expected false-alarm statistics.
* Fixed seed produces identical outputs.
* Increased clutter increases false alarms.
* Track truth and detection timestamps align.

#### Dynamic tests

* Static body produces no propulsor sideband.
* Rotating component produces sideband structure.
* Rotation-rate perturbation changes sideband spread.
* Dynamic phase sampling warning appears when undersampled.

#### Dataset tests

* No object leakage across train/test.
* No seed leakage across train/test.
* All artifacts contain provenance.
* All source-card confidence labels present.
* Banned-reference scanner passes.
* Optional plugins do not run in core CI.

# 9. Credibility scoring

Each artifact receives a credibility score.

```yaml
credibility:
  grade: silver
  validation_tier: V2
  components:
    schema: pass
    analytic: pass
    solver_compare: pass_with_warnings
    material_confidence: bronze
    geometry_confidence: silver
    measured_calibration: none
  final_claim:
    allowed: "public-proxy synthetic benchmark artifact"
    disallowed: "exact real-platform signature"
```

## Suggested scoring formula

```text
credibility_score =
  0.20 * schema_quality
+ 0.20 * analytic_validation
+ 0.20 * solver_consistency
+ 0.15 * material_confidence
+ 0.15 * geometry_confidence
+ 0.10 * radar_chain_validation
```

Then map:

|     Score | Grade        |
| --------: | ------------ |
| 0.90–1.00 | Platinum     |
| 0.75–0.89 | Gold         |
| 0.55–0.74 | Silver       |
| 0.30–0.54 | Bronze       |
|     <0.30 | Experimental |

A public-proxy artifact with no measured calibration should not exceed Gold, and usually should not exceed Silver unless solver comparison and public literature validation are strong.

# 12. GPU-enabled Docker design

## Container philosophy

Use multiple containers:

```text
echoforge-api          FastAPI service
echoforge-worker       Python/Ray worker
echoforge-rcs-gpu      CUDA RCS solver container
echoforge-radar-gpu    radar-chain GPU container
echoforge-ui           Studio frontend
echoforge-db           Postgres
echoforge-objectstore  MinIO/S3-compatible storage
echoforge-dev          developer shell
```

GPU access should be handled through Docker/NVIDIA tooling, not custom host hacks. Docker Compose supports GPU device reservations, and NVIDIA Container Toolkit provides the GPU runtime integration needed for GPU-accelerated containers. ([Docker Documentation][7])

## Compose sketch

```yaml
services:

    environment:
      ECHOFORGE_STORAGE: s3
      ECHOFORGE_DB: postgres
    depends_on:
      - postgres
      - minio

  worker:
    build: ./services/worker
    environment:
      RAY_ADDRESS: auto
    depends_on:
      - api
      - minio
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: ["gpu"]

  rcs_gpu:
    build: ./containers/rcs-gpu
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: ["gpu"]

  radar_gpu:
    build: ./containers/radar-gpu
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: ["gpu"]

  ui:
    build: ./apps/studio
    ports:
      - "3000:3000"

  postgres:
    image: postgres:16

  minio:
    image: minio/minio
```

## Job scheduling

Ray is appropriate for distributed execution because it supports tasks/actors and resource-aware scheduling, including GPU resource requests. Use Ray for simulation sweeps and parallel scenario generation; use a workflow layer only when durable multi-stage workflows become necessary. ([Ray][8])

# 14. CLI design

```bash
# Validate mesh and create asset card
echoforge asset import ./mesh.obj \
  --object-id uav.public_proxy.medium_delta_low_altitude_v1 \
  --materials ./materials.yaml \
  --out ./artifacts/assets/

# Run RCS sweep
echoforge rcs sweep ./artifacts/assets/object.asset.yaml \
  --sweep ./sweeps/generic_band_sweep.yaml \
  --solver sagitta_sbr \
  --gpu 0 \
  --out ./artifacts/signatures/

echoforge validate signature ./artifacts/signatures/example.echosig \
  --analytic \
  --solver-spot-check openems \
  --out ./reports/signature_validation.html

echoforge scenario generate ./scenarios/low_altitude_hardneg.yaml \
  --seed 1234 \
  --out ./artifacts/scenarios/

echoforge radar run ./artifacts/scenarios/scenario.yaml \
  --radar-card ./radars/generic_pulse_doppler_array.yaml \
  --out ./artifacts/radar_runs/

# Assemble dataset
echoforge dataset build ./dataset_cards/low_altitude_proxy_hardneg.yaml \
  --out ./datasets/low_altitude_proxy_hardneg_v1/

# Run baseline benchmark
echoforge benchmark run ./datasets/low_altitude_proxy_hardneg_v1 \
  --baseline cfar_kalman \
  --out ./reports/benchmark_baseline.html
```
