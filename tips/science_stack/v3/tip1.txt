# 4. Cross-proposal synthesis: what the final system must be

The winning design principles are:

1. **Strict-open core.** EchoForge must run without closed binaries, license files, or source-restricted packages. Optional adapters are allowed, but not required.

2. **Proxy signatures, not truth claims.** Public-source object packs should produce **uncertainty-bounded proxy signatures**. They should never be marketed as measured or authoritative real-world signatures.

3. **RCS is a tensor.** Store complex scattering/polarimetric data where available, not just scalar dBsm.

4. **Hard negatives are a product pillar.** Birds, flocks, commercial drones, kites, balloons, insects, turbines, cranes, towers, vehicles, ground clutter, terrain glints, weather, RFI, multipath ghosts, and sensor artifacts must be modeled as seriously as target classes.

5. **Radar chain is first-class.** EchoForge should output raw/baseband IQ, range-Doppler, range-Doppler-angle, detections, tracks, benchmark splits, validation reports, and dataset cards.

6. **Validation is a feature, not a phase.** Every artifact needs validation tier, solver regime, uncertainty, mesh/material provenance, and known limitations.

7. **GPU containers must be boring.** The default Docker path should have a GPU doctor, pinned CUDA/CuPy/PyTorch/JAX versions, solver images, smoke tests, and chunked campaign execution. NVIDIA’s container runtime supports Docker GPU enumeration through `--gpus` or `NVIDIA_VISIBLE_DEVICES`, so EchoForge should expose this cleanly through its compose and CLI workflows. ([NVIDIA Docs][5])

# 6. Product definition

**EchoForge** is a strict-open, GPU-native synthetic sensing foundry for generating, validating, and packaging uncertainty-bounded radar/RF/EO/acoustic-style datasets from public object proxies, material assumptions, motion models, sensor archetypes, and cluttered worlds.

The professional promise:

> EchoForge produces **traceable synthetic proxy observations with validation grades**, not unverifiable measured-truth signatures.

The fun/product identity:

> Users “forge” synthetic echoes from objects, environments, and sensors. The UI can lean into the anvil/radar-ring metaphor, but the engineering core must feel like a serious scientific platform.

Primary v1 focus:

```text
Radar/RCS first:
  - object/mesh/material ingestion
  - GPU high-frequency RCS sweeps
  - strict-open radar-chain simulator
  - low-altitude cluttered scenarios
  - hard-negative worlds
  - detections/tracks
  - dataset/benchmark release
  - validation dossiers
```

Secondary v1.5/v2 modules:

```text
RF cue metadata
EO/IR metadata or lightweight renders
Acoustic cue features
Lidar-like reflection products
Full multimodal fusion
```

Explicit non-goals for v1:

```text
No proprietary radar clone.
No claim of exact real target signature.
No decoy/evasion optimizer.
No engagement/defeat workflow.
No closed dependency in the required core.
No UI-first development before physics and validation work.
```

## 7.2 License architecture

Recommended split:

```text
echoforge-core: Apache-2.0 or MIT
echoforge-sdk: Apache-2.0 or MIT
echoforge-ui: Apache-2.0 or MIT
echoforge-radar: Apache-2.0 or MIT
echoforge-schemas: Apache-2.0 or MIT

GPL/AGPL solvers:
  - isolated as external containers/processes
  - no silent static embedding
  - clear license metadata in manifests
  - source/commit/container digest recorded

Optional restricted/source-gated plugins:
  - never required for core operation
  - runtime license detection
  - dataset manifests disclose use
  - CI has strict-open mode that passes without them
```

HermesPy can be useful as an optional open reference path, but its AGPLv3 licensing means it must be isolated or handled deliberately. ([HermesPy][9])

## 10.2 RCS cube schema

Store complex scattering where possible. Do **not** store only pretty dB plots.


Critical rule:


# 11. Object library design

## 11.1 Object confidence tiers

| Tier | Meaning                                     | Allowed use                                  |
| ---- | ------------------------------------------- | -------------------------------------------- |
| T0   | Placeholder geometry                        | Internal tests only.                         |
| T1   | Generic synthetic shape                     | Algorithm smoke tests.                       |
| T2   | Public-source proxy geometry                | Research datasets with caveats.              |

# 12. Material and uncertainty subsystem

This is a must-have. Radar experts will immediately challenge vague words like “fiberglass,” “carbon fiber,” or “composite.”

Material cards should separate:

```text
Physical material prior:
  - permittivity distribution
  - conductivity distribution
  - loss tangent distribution
  - permeability distribution
  - anisotropy flag
  - roughness distribution
  - thickness distribution
  - frequency validity range

Solver-supported representation:
  - PEC
  - impedance boundary
  - dielectric volume
  - surface coating
  - effective attenuation/scattering surrogate

Uncertainty model:
  - parameter distribution
  - source confidence
  - sampling seed
  - validation status
```

Material realism gates:

```text
M0: Material label exists only.
M1: Region-tagged material card exists.
M2: Frequency-dependent prior exists.
M3: Solver-supported representation is explicit.
M4: Component/submodel full-wave validation exists.
M5: Measured coupon or open measured calibration exists.
```

# 15. Hard-negative and false-positive library

The hard-negative engine should not be an afterthought. It is one of the main reasons EchoForge will be valuable.

## 15.1 Taxonomy

```text
Biological airborne:
  - single bird
  - flock
  - bats
  - insect cloud

Civilian/benign airborne:
  - quadcopter
  - hexacopter
  - RC fixed wing
  - hobby glider
  - kite
  - balloon
  - debris/plastic bag

Infrastructure:
  - wind turbine
  - tower
  - crane
  - power line
  - rooftop HVAC
  - moving construction equipment

Vehicles and surface movers:
  - trucks
  - cars
  - motorcycles
  - boats
  - trains where relevant

Environment:
  - terrain glint
  - ground clutter
  - vegetation
  - rain
  - dust/haze proxy
  - sea/shore clutter where relevant

Sensor/system artifacts:
  - RFI burst
  - multipath ghost
  - sidelobe artifact
  - dropped pulses
  - calibration drift
  - saturation
```

## 15.2 Difficulty tiers

| Tier | Meaning                                                                      |
| ---- | ---------------------------------------------------------------------------- |
| H0   | Clean negative, obviously not target-like.                                   |
| H1   | Similar size but distinct motion/signature.                                  |
| H2   | Similar range-Doppler behavior.                                              |
| H3   | Similar RCS/aspect behavior under some conditions.                           |
| H4   | Multi-confuser scene causing false tracks.                                   |
| H5   | Domain-shift stress test with unseen object/environment/sensor combinations. |

## 15.3 Hard-negative mining loop

```text
1. Generate mixed target/confuser/clutter scenes.
2. Run baseline detector/classifier/tracker.
3. Find false positives, false tracks, missed detections.
4. Cluster failure modes.
5. Generate new benign/ambiguous variants around failure modes.
6. Add to hard-negative curriculum.
7. Rebuild benchmark splits with leakage controls.
8. Report robustness improvements and remaining failures.
```

This is for **robust detection and false-alarm reduction**, not for designing evasion artifacts.

