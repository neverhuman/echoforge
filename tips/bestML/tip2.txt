Great. With your toolchain and dataset validation now passing, here is the ranked research cut I would use for **EchoForge-style raw radar → ML feature construction**, especially for **low/slow propeller UAVs such as Shahed/Geran-class targets**.

I treated “ALL publications” as a coverage problem across the major radar ML publication families: micro-Doppler, FMCW radar cubes, HRRP, SAR/ISAR ATR, point clouds, track-level classification, RCS statistics, multistatic/multiband fusion, polarimetry, clutter/STAP, and learned raw-I/Q approaches. The ranking below is **not novelty-ranked**. It is ranked by practical value for real detection/classification: robustness, explainability, sample efficiency, known published performance, deployability, and usefulness under clutter.

## The answer in one sentence

The best human approach is **not one feature**: it is a **physics-guided fused feature bank** built from calibrated raw I/Q into **range-Doppler-angle tensors, gated micro-Doppler, CFAR/clutter/RCS metadata, and short-window track kinematics**, then trained with strong tabular/time-series baselines before moving to heavier deep models.

For your current scale, around **3,900 records**, I would prioritize **feature-rich, physics-guided models** over raw end-to-end deep learning. Radar ATR reviews repeatedly note that deep learning is promising but often limited by sample size, radar-condition mismatch, and domain complexity, while embedded radar ML guidance emphasizes representative data, train/test separation, and careful feature-block design. ([MDPI][15])

# My recommended canonical EchoForge feature stack

For your current direction, I would make the feature pipeline **strictly layered**:

## Layer 1 — Raw-to-physics transforms

Every record should preserve provenance and then produce:

```text
raw_iq
  -> calibration / DC removal / clutter suppression
  -> range profile or range FFT / matched filter
  -> Doppler FFT
  -> angle FFT / beamforming / MUSIC where antenna data exists
  -> CFAR detections + local clutter metadata
```

Canonical outputs:

```text
range_profile
range_doppler_map
range_angle_map
doppler_angle_map
range_doppler_angle_cube
detection_list[x, y, z/range, vr, snr, rcs_proxy, cfar_margin]
```

This follows the conventional radar-cube path: raw fast-time/slow-time/spatial samples are transformed into range, Doppler, and angle representations. ([arXiv][16])

## Layer 2 — Target-gated micro-Doppler

For each candidate target or track:

```text
track/range gate
  -> phase-stable slow-time signal
  -> STFT spectrogram
  -> cepstrogram / cadence-velocity diagram
  -> rotor/blade periodicity features
```

Features I would compute immediately:

```text
md_bandwidth
md_centroid
md_entropy
md_peak_count
md_harmonic_spacing
md_sideband_symmetry
md_blade_flash_rate
md_high_freq_energy_ratio
md_body_to_rotor_energy_ratio
md_periodicity_score
```

Micro-Doppler should be treated as a **high-value but conditional** signal: excellent when visible, not safe as the only feature. NeXtRAD UAV measurements show that micro-Doppler visibility depends heavily on SNR, material, aspect, and band. ([UCL Discovery][26])

## Layer 3 — Track and behavior windows

For each target track, create short windows, for example 1 s, 3 s, 5 s, and 10 s:

```text
mean_vr
mean_ground_speed
acceleration
jerk
turn_rate
curvature
heading_stability
altitude_stability
climb_rate
range_rate_consistency
track_covariance
missed_detection_rate
detection_persistence
```

This matters because many real engagements will have **weak or intermittent micro-Doppler**. Track-only drone classification has published support precisely for cases where visual, RF, acoustic, or micro-Doppler cues are unavailable at range.

## Layer 4 — RCS / amplitude / detector context

Add cheap, robust metadata:

```text
snr_mean
snr_std
snr_min
snr_max
rcs_proxy_mean
rcs_proxy_cv
amplitude_scintillation
cfar_threshold_margin
local_noise_floor
local_clutter_density
doppler_notch_distance
range_bin_persistence
```

These features are very deployable and help the model learn when the radar itself is uncertain.

## Layer 5 — Fusion model

Start with models that do not require massive data:

```text
LightGBM / XGBoost
Random Forest
RBF SVM
logistic calibration layer
small temporal CNN / TCN for sequences
small CNN for range-Doppler / micro-Doppler images
```

Then graduate to heavier models only after ablation proves the feature bank is saturated:

```text
ConvLSTM
small Vision Transformer on radar maps
GNN / graph signal processing for point clouds
complex-valued raw-IQ encoder
self-supervised radar foundation encoder
```

For the dataset size you described, I would expect the strongest first production baseline to be:

```text
[range-doppler summary features
 + micro-doppler compact features
 + RCS/SNR/CFAR metadata
 + 3-5 second track kinematics]
 -> LightGBM / XGBoost / Random Forest ensemble
 -> calibrated probability
```

Then run CNNs on the map products as a second branch.

# Best references to anchor the implementation

The core papers and surveys I would treat as the “must-read spine” are:

1. **V. C. Chen et al., “Micro-Doppler effect in radar: phenomenon, model, and simulation study”** — foundational micro-Doppler physics for rotating/vibrating/tumbling targets. ([Rowan University][17])
2. **Chen, Tahmoush, Miceli, *Radar Micro-Doppler Signatures: Processing and Applications*** — book-length treatment of micro-Doppler processing and applications. ([The IET Digital Library][28])
3. **Harmanny, de Wit, Cabic, “Radar micro-Doppler feature extraction using the spectrogram and the cepstrogram”** — directly relevant to bird/UAV discrimination. ([TNO Publications][18])
4. **NeXtRAD/UCL multistatic UAV micro-Doppler measurements** — very relevant because it shows real UAV/bird differences and the role of X/L-band, monostatic/bistatic geometry, polarization, SNR, and RCS. ([UCL Discovery][26])
5. **Narayanan/Tsang/Bharadwaj drone/bird micro-Doppler work** — useful performance anchor for spectrogram-image classification. ([Penn State][29])
6. **Cranfield/NATO kinematic drone classification work** — crucial reminder that track-level features can work when micro-Doppler is unavailable.
7. **CubeLearn / radar cube learning literature** — important for raw ADC/FMCW-to-range/Doppler/AoA conversion and learnable preprocessing. ([arXiv][16])
8. **Remote Sensing 2023 RATR review** — broad radar target recognition map across motion, micro-motion, HRRP, SAR, ISAR, and deep learning limitations. ([MDPI][15])
9. **SAR ATR survey literature** — important for scattering centers, template methods, texture/geometry, sparse representation, and the older human-engineered ATR tradition. ([MDPI][24])
10. **Radar point-cloud ML / graph signal processing work** — relevant if your sensors output sparse 3D/4D detections. ([ResearchGate][30])

# Final practical ranking for your project

For **EchoForge right now**, I would implement in this order:

1. **Range-Doppler-Angle cube products**
2. **Gated STFT micro-Doppler**
3. **Compact micro-Doppler periodicity / cepstral features**
4. **Track kinematic windows**
5. **RCS/SNR/CFAR/clutter metadata**
6. **HRRP if bandwidth supports it**
7. **Point-cloud features if MIMO/mmWave detections exist**
8. **Multistatic/multiband/polarimetric fusion if channels exist**
9. **STAP/MTI residual features for low-altitude clutter**
10. **Learned raw-IQ encoders only after the above baselines are locked**

That is the “no-regrets” path: preserve physics, make every feature auditable, keep raw/cube/timeseries products available, and train models that can win with thousands—not millions—of examples.
