I would **throw out the current AUC table as invalid until proven otherwise**. An AUC of 1.0 on a 1,500-row holdout with a 0.216667 positive rate means roughly **325 positives and 1,175 negatives**, or **381,875 positive-negative score comparisons with zero ranking inversions**. Getting that across CFAR/TBD, LightGBM, CatBoost, TCN, and a transformer is not a normal “good radar model” signature. It is a **simulator/evaluation artifact signature**.

I treated this as a **simulation-validity and leakage audit**, not an operational targeting report. I also cannot honestly claim to have reviewed literally every radar publication online, but I did scan the repo and anchor the recommendations in major public literature on drone/bird radar signatures, micro-Doppler, low-grazing clutter, CFAR, propagation, multipath, weather attenuation, and measured multi-sensor datasets.

## Executive finding

EchoForge, as currently public, looks like a promising scaffold, but not yet a physically validated radar simulator. The README describes it as a “strict-open” synthetic sensing foundry intended to produce **public-proxy** signatures, uncertainty-scored RCS artifacts, radar-chain products, hard-negative worlds, validation reports, and benchmark packages; it also explicitly says not to make exact measured-truth claims without lawful measured data and provenance. ([GitHub][1])

Your public scenario/config files are full of exactly the fields that can make ML trivially separable: object identity, preset identity, label-like priors, expected observable bins, SNR ranges, fixed hard-negative families, and synthetic target parameter boxes. The public scenario is marked synthetic/unvalidated, with placeholder references and fixture warnings, and the validation docs define higher measured-data validation tiers as deferred or dependent on lawful measured data. ([GitHub][2])

The Rust radar simulator also appears to be a compact proxy chain: it injects a target-like delayed waveform with target amplitude controlled by a target-SNR parameter, scalar RCS, simplified micro-motion/scintillation/glints/RFI/clutter, followed by simple CFAR-style processing. That is very useful for scaffolding and tests, but it is not yet a real radar scene simulator with full propagation, antenna, receiver, coherent IQ, target scattering, clutter maps, and field validation. ([GitHub][3])

## Most likely reason your AUCs are 1.0

The most likely cause is **not model quality**. It is one or more of these, ranked:

1. **Label or generator metadata leakage** into features: object class, scenario name, preset, `classification_prior`, expected range/Doppler bins, SNR, target-present flags, horizon fields, or post-label detection products.
2. **Split leakage**: train/validation/holdout likely share the same generator seeds, target parameter distributions, environment presets, object families, and negative families.
3. **Synthetic separability**: positives and negatives may be generated by different processes rather than by the same physical radar chain plus different scene contents.
4. **Baseline score already solves the problem**: baseline AUCs of 0.9656, 0.9892, and 0.9995 mean the task is nearly solved before ML.
5. **Causal horizon mismatch**: if “5 s / 15 s / 45 s” labels are produced from whole-episode information or future samples, the model is not doing early detection.
6. **Unrealistic base rates**: the holdout positive rate is exactly constant at 0.216667 across horizons, which is convenient for benchmark balance but not representative of real low-altitude surveillance false-alarm economics.

# Ranked technical report: missing or incorrect real-world artifacts

## 1. P0 — Leakage-proof experiment design

**Impact:** Highest. Until this is fixed, no physics improvement matters.

**What is likely wrong:** Your simulator config contains fields that are close to labels or label priors: object identity, scenario identity, target preset, `classification_prior`, expected range-bin ranges, expected Doppler-spread bins, target SNR, and sensor-observable hints. If any of those or their deterministic derivatives enter the ML table, AUC=1.0 is expected.

**Technical work:**

* Create a hard separation between:

  * **latent generator state**: object ID, target family, preset, SNR, seed, environment, scenario recipe;
  * **observable radar products**: raw IQ, range-compressed IQ, range-Doppler maps, detections, tracks;
  * **labels**: causal target-present / detection labels.
* Build a `feature_sanitizer` that fails the pipeline if columns contain `label`, `class`, `target`, `preset`, `scenario`, `seed`, `snr`, `prior`, `horizon`, `expected_*`, `observable_hint`, `range_bin_truth`, or `doppler_truth`.
* Add a **metadata-only leakage probe**: train LightGBM/CatBoost on only metadata. If AUC > 0.55, the split/task is contaminated.
* Add a **random-label probe**: shuffled labels must return AUC ≈ 0.5.
* Add a **negative-control feature probe**: nonphysical IDs, timestamps, row numbers, file paths, and scenario hashes must not predict labels.
* Split by **entire scenario groups**, not rows. Hold out complete combinations of object family, environment, sensor configuration, generator seed, day/site, and hard-negative class.

**Acceptance gate:** AUCs are not reportable unless metadata-only, ID-only, and shuffled-label baselines are all near chance.

---

## 2. P0 — Measured-data anchoring and validation tiers

**Impact:** Highest. A synthetic simulator without measured anchoring can look perfect while learning its own artifacts.

EchoForge’s own repo posture is correct: public-proxy signatures should not be treated as measured truth without lawful measured data and explicit provenance. The validation-tier document also distinguishes unvalidated/analytic/cross-solver levels from measured-data validation. ([GitHub][1])

**Technical work:**

* Define validation levels:

  * **unvalidated:** toy/fixture simulation.
  * **basic:** analytic checks: radar equation, range resolution, Doppler resolution, thermal noise.
  * **cross_checked:** cross-solver agreement: independent waveform/CFAR/RCS modules.
  * **benchmarked:** lab calibration: corner reflectors, known rotating targets, controlled reflectors.
  * **benchmarked:** controlled outdoor range: measured benign UAVs, birds, vehicles, clutter.
  * **measured:** blind measured holdout: different day/site/weather/sensor configuration.
* Use public measured datasets where possible. Recent public work includes time-synchronized drone datasets acquired from multiple radars/RF receivers, and the dataset literature explicitly notes micro-Doppler signatures from rotating propellers and structural vibration as useful drone-discrimination signals. ([Nature][4])
* Report **sim-to-real error**, not just classifier AUC: distributions of RCS, Doppler centroid, Doppler spread, micro-Doppler line spacing, range-bin migration, CFAR false alarms, track fragmentation, and score calibration.

**Acceptance gate:** A model trained on simulation must be tested on measured data not used for simulator tuning.

---

## 3. P0 — Real radar equation, range loss, and SNR budget

**Impact:** Extremely high. Your current simulator appears to set target strength from a target-SNR parameter instead of deriving received power from the physical chain.

**What is missing:**

* Transmit power / EIRP.
* Antenna gain and scan loss.
* Two-way path loss, including the radar-equation (R^{-4}) dependence.
* RCS as a function of aspect, frequency, polarization, and configuration.
* Receiver noise temperature, noise figure, bandwidth, processing gain.
* Loss terms: radome, cable, digitizer, windowing, pulse compression, CFAR loss, integration loss.
* Clutter-to-noise and signal-to-clutter ratios, not just signal-to-noise.

**Technical work:**

* Replace `target_snr_db` as a direct generation knob with a physical link budget.
* Preserve `target_snr_db` only as a derived diagnostic.
* Generate the received complex voltage after applying propagation, target scattering, antenna response, receiver gain, noise, and digitization.
* Report (P_d) at fixed (P_{fa}), not just AUC.

**Acceptance gate:** If you double the target range, received power should change approximately according to two-way radar path loss unless multipath/clutter dominates.

---

## 4. P0 — Complex IQ chain instead of magnitude-only proxies

**Impact:** Extremely high. Micro-Doppler, Doppler ambiguity, coherent integration, phase noise, and clutter suppression all require complex slow-time behavior.

The micro-Doppler literature emphasizes phase-coherent radar measurement and time-frequency processing. Rahman and Robertson measured drone and bird micro-Doppler at K-band and W-band and discuss how Doppler signatures depend on time-frequency resolution, chirp repetition, aliasing, propeller signatures, and bird wingbeats. ([Nature][5])

**What is likely wrong:** If slow-time processing is performed over magnitudes rather than complex IQ, the simulator cannot faithfully model coherent Doppler, phase noise, range migration, clutter cancellation, or micro-Doppler physics. The public Rust code appears compact and proxy-like rather than a full complex radar data-cube simulator. ([GitHub][3])

**Technical work:**

* Store raw simulated data as complex IQ with dimensions like:

  * pulse / chirp index,
  * fast-time sample or range bin,
  * receive channel,
  * polarization where relevant.
* Implement:

  * waveform generation,
  * propagation delay,
  * phase accumulation,
  * dechirp or matched filtering,
  * range FFT / pulse compression,
  * Doppler FFT over complex slow time,
  * windowing,
  * range-Doppler maps,
  * CFAR/detector products,
  * track products.
* Do not let the ML model see oracle target locations or synthetic state variables.

**Acceptance gate:** A pure Doppler tone, moving point target, static clutter patch, and rotating-blade target should reproduce analytic range-Doppler/micro-Doppler expectations.

---

## 5. P0 — Target RCS is not a scalar box

**Impact:** Extremely high.

The current public config uses broad RCS ranges and scalar/material placeholders. That is not sufficient for real detection modeling. Drone/bird research repeatedly shows that small aerial targets can overlap in size, altitude, speed, and RCS; RCS alone is inadequate for robust discrimination. ([Nature][5])

**Missing artifacts:**

* Aspect-dependent RCS.
* Frequency dependence.
* Polarization dependence.
* Structural scattering centers.
* Material permittivity/conductivity variation.
* Surface roughness.
* Engine/propeller/nose/wing/body contributions.
* Payload/configuration changes.
* Ground-proximity effects during takeoff.
* Multipath-modified apparent RCS.

**Technical work:**

* Use a scattering-center model at minimum.
* For higher fidelity, use EM solvers or validated approximations:

  * physical optics,
  * shooting and bouncing rays,
  * method of moments for smaller components,
  * FDTD/FEM for selected validation cases.
* Produce RCS distributions by aspect angle, elevation, frequency, polarization, and configuration.
* Calibrate with lawful measured RCS data where available. In-flight drone/bird RCS measurement work exists at K-band and W-band and should be treated as an anchor for order-of-magnitude realism. ([ietresearch.onlinelibrary.wiley.com][6])

**Acceptance gate:** The same target should not have a fixed separable signature across all scenes; its apparent signature must change with aspect, geometry, propagation, and sensor mode.

---

## 6. P0 — Propeller and micro-Doppler physics

**Impact:** Very high, especially for small UAV discrimination.

Rahman and Robertson show that drones and birds both induce micro-Doppler signatures, but drones can show propeller-related sidebands and blade-flash behavior while birds show wingbeat-dependent signatures. Their work also notes aliasing and time-frequency tradeoffs, which means the simulator must model sampling and processing, not just add a generic “micro_doppler_hz” value. ([Nature][5])

**What is likely wrong:** A single sinusoidal amplitude modulation or broad micro-Doppler range is not enough.

**Technical work:**

* Model rotating blades as moving scattering centers.
* Include:

  * blade count,
  * blade length,
  * RPM distribution,
  * RPM transients during throttle changes,
  * material/reflectivity,
  * blade pitch,
  * hub/body scattering,
  * engine vibration,
  * attitude-induced visibility,
  * aliasing from PRF/chirp repetition.
* Model birds as wing/body scattering systems, not just random negatives. Bird-vs-drone measured micro-Doppler classification has been studied with 10 GHz CW radar and multiple bird/drone classes, with performance far below perfect for fine-grained classes. ([MDPI][7])

**Acceptance gate:** The same target at two PRFs should show plausible micro-Doppler aliasing differences; birds should sometimes be hard negatives, not trivially separable.

---

## 7. P0 — Low-grazing propagation and ground multipath

**Impact:** Very high for low-altitude/takeoff scenarios.

Low-altitude radar detection at low grazing angles is specifically hard because terrain clutter and ground reflections pollute the signal. Ezuma et al. studied micro-UAV detection with a surface-sited 24 GHz FMCW radar in rocky terrain and explicitly modeled land clutter with a Weibull distribution while using CFAR plus micro-Doppler/trajectory features. ([arXiv][8])

RF propagation tools and radar vertical coverage models include refracted paths and multipath fading from direct plus ground-reflected rays, with surface dielectric constant, surface roughness, vegetation, and slope affecting the result. ([MathWorks][9]) Low-angle target localization literature also emphasizes that complex ground reflections can severely degrade height/location estimation. ([Nanyang Technological University][10])

**Technical work:**

* Add two-ray and multi-ray ground reflection.
* Add terrain elevation and local slope.
* Add surface dielectric/roughness/vegetation cover.
* Model occlusion and partial line of sight.
* Model refractivity and Earth curvature where appropriate.
* Include buildings, ridges, power lines, trees, and ground vehicles as reflectors.
* During takeoff, model transition from ground clutter proximity to airborne separation.

**Acceptance gate:** A low-altitude target near the horizon should sometimes fade, split, ghost, or suffer height/range errors due to multipath.

---

## 8. P0 — Non-Gaussian, nonstationary clutter

**Impact:** Very high.

Real clutter is not simple white Gaussian noise plus a small correlated term. Low-grazing land/sea clutter can be non-Rayleigh; Weibull distributions are used for land/sea clutter in low-grazing, high-resolution settings. ([ScienceDirect][11]) High-resolution radar clutter can also be non-Gaussian, and K-distributed clutter is a standard sea-clutter model. ([dst.defence.gov.au][12])

**Missing artifacts:**

* Terrain-dependent clutter maps.
* Heavy-tailed clutter.
* Clutter spikes.
* Spatial correlation.
* Temporal correlation.
* Range-dependent clutter power.
* Doppler-spread clutter from wind/vegetation.
* Moving clutter: birds, insects, vehicles, people, livestock, machinery.
* Urban multipath and glints.
* Sea/lake/rain clutter where relevant.

**Technical work:**

* Implement multiple clutter distributions:

  * Rayleigh/exponential for simple thermal-like clutter,
  * Weibull for land/sea low-grazing cases,
  * K-distribution / compound Gaussian for spiky clutter,
  * log-normal where appropriate,
  * mixture models for urban/semi-urban scenes.
* Use clutter maps with site-specific parameters.
* Add correlated texture fields rather than independent per-cell samples.
* Tune clutter distributions from measured background-only data.

**Acceptance gate:** CFAR false alarms should cluster in hard terrain/weather conditions, not appear as independent random dots.

---

## 9. P0 — CFAR/detector modeling beyond simple CA-CFAR

**Impact:** Very high.

The repo has CA-CFAR-style logic. CA-CFAR is a useful baseline, but real nonhomogeneous clutter and multiple-target situations require careful detector modeling. Rohling’s ordered-statistic CFAR work discusses the limitations of average-based CFAR and the motivation for ordered-statistic methods in nonstationary clutter and multiple-target cases. 

**Technical work:**

* Implement and compare:

  * CA-CFAR,
  * GO-CFAR,
  * SO-CFAR,
  * OS-CFAR,
  * 2D range-Doppler CFAR,
  * clutter-map CFAR,
  * adaptive thresholding under Weibull/K clutter,
  * track-before-detect for weak targets.
* Report false alarms by clutter regime.
* Include CFAR loss and edge effects.
* Prevent CFAR outputs from becoming oracle labels.

**Acceptance gate:** Detector performance must degrade in nonhomogeneous clutter, clutter edges, multiple-target scenes, and heavy-tailed backgrounds.

---

## 10. P0 — Causal takeoff dynamics

**Impact:** High.

A “taking off from the ground” scene is not just an airborne target with altitude sampled from a box. The early phase is dominated by runway/ground clutter, attitude changes, acceleration, changing aspect, possible occlusion, and range-Doppler migration.

**Technical work:**

* Model phases:

  * stationary/pre-launch ground object,
  * ground roll,
  * rotation/liftoff,
  * initial climb,
  * turn/climb,
  * acceleration/deceleration.
* Couple kinematics to attitude:

  * pitch during rotation,
  * yaw/roll changes,
  * aspect-angle changes,
  * throttle/RPM changes.
* Include wind:

  * headwind/tailwind/crosswind,
  * gusts,
  * turbulence,
  * wind shear near terrain.
* Use continuous trajectories, not independent sampled speed/altitude/radial velocity fields.
* Generate causal windows: for a 5-second horizon, the model may only see samples available up to that time.

**Acceptance gate:** A 5-second early-detection task should be substantially harder than a 45-second task unless the target is trivially visible at launch.

## 11. P1 — Antenna, scan, beam, sidelobe, and dwell modeling

**Impact:** High.

Real radar data depends heavily on antenna behavior. A simulator that omits beams and sidelobes can create unrealistically clean data.

**Missing artifacts:**

* Beam shape.
* Sidelobes.
* Scan schedule.
* Dwell time.
* Revisit rate.
* Beam squint.
* Polarization.
* Monopulse or array channel behavior.
* Elevation coverage gaps.
* Calibration errors.
* Platform/sensor pointing uncertainty.

**Technical work:**

* Add antenna gain patterns as functions of azimuth/elevation/frequency/polarization.
* Apply scan loss and dwell-dependent coherent processing interval.
* Model sidelobe detections and clutter entering through sidelobes.
* For array radars, simulate per-channel phase and calibration errors.

**Acceptance gate:** The same scene should produce different observability depending on beam dwell, pointing, and sidelobe interactions.

## 12. P1 — Weather and atmospheric effects

**Impact:** High, especially above X/Ku/K bands or in rain.

Rain attenuation is frequency-, polarization-, rainfall-rate-, and elevation-angle-dependent under ITU-R P.838-style models. ([MathWorks][13])

**Technical work:**

* Add:

  * rain attenuation,
  * rain clutter,
  * fog/cloud attenuation where relevant,
  * humidity/gaseous absorption,
  * temperature-dependent noise effects,
  * wind-driven vegetation clutter,
  * storm-cell spatial variability.
* Weather should be a field over space/time, not a single scalar.

**Acceptance gate:** Detection range and false-alarm rate should change plausibly with rainfall rate, frequency, and polarization.

## 13. P1 — Receiver impairments and calibration errors

**Impact:** High.

The current code has some proxy phase/noise/scintillation/RFI knobs, but real receivers include many coupled imperfections.

**Technical work:**

* Model:

  * phase noise,
  * chirp nonlinearity,
  * timing jitter,
  * I/Q imbalance,
  * DC offsets,
  * ADC quantization,
  * clipping/saturation,
  * AGC behavior,
  * receiver gain drift,
  * channel-to-channel phase/gain mismatch,
  * temperature drift,
  * missing pulses,
  * dropped samples,
  * timestamp jitter.
* Add calibration routines and calibration failure modes.

**Acceptance gate:** Small receiver changes should sometimes produce domain shift between train and holdout.

## 14. P1 — RFI and electromagnetic environment

**Impact:** High.

A few impulse-noise samples are not enough. Real RF environments contain structured emitters and interference.

**Technical work:**

* Add:

  * co-channel emitters,
  * bursty interference,
  * sweepers,
  * adjacent-channel leakage,
  * intermodulation,
  * self-interference,
  * communications emitters,
  * other radars,
  * hardware clock artifacts.
* Make RFI scene-dependent and time-correlated.
* Include false detections and corrupted tracks caused by RFI.

**Acceptance gate:** Models should not treat RFI as a simple noise distribution that can be averaged away.

## 15. P1 — Hard negatives are far too shallow

**Impact:** High.

The repo has hard-negative object packs, but the public cards are fixture-like and sparse. ([GitHub][14]) A real low-altitude radar scene must include negatives that overlap target signatures.

**Needed hard negatives:**

* Birds by species, size, flocking behavior, wingbeat frequency.
* Commercial quadrotors and fixed-wing RC aircraft.
* Balloons, kites, debris, plastic bags.
* Bats/insects in some environments.
* Ground vehicles with multipath/side-lobe returns.
* Wind turbines and rotating machinery.
* Power lines, towers, cranes.
* Rain cells and clutter spikes.
* Sea/lake glints if relevant.
* Terrain/building ghosts.
* Multiple simultaneous benign objects.

**Technical work:**

* Build a measured hard-negative library.
* Ensure hard negatives use the same radar chain as positives.
* Hold out entire negative families during validation.
* Report confusion by negative class, not aggregate AUC only.

**Acceptance gate:** Bird-vs-drone and drone-vs-drone subclass performance should be materially below perfect on unseen measured cases.

## 16. P1 — Base-rate and false-alarm economics

**Impact:** High.

AUC can be misleading for rare-event radar detection. A holdout positive rate of 21.7% is not representative of many surveillance settings. In real systems, false alarms per hour, per square kilometer, per scan, or per track are often more important than aggregate ROC AUC.

**Technical work:**

* Report:

  * (P_d) at fixed (P_{fa}),
  * false alarms per hour,
  * false tracks per hour,
  * median time to detection,
  * probability of detection before a causal horizon,
  * track purity,
  * track fragmentation,
  * calibration curves,
  * precision-recall at realistic base rates.
* Evaluate at very low false-alarm regimes.
* Use confidence intervals and bootstrap by scenario group, not row.

**Acceptance gate:** A model with AUC 0.99 but too many false tracks should be considered operationally poor.

## 17. P1 — Track formation and data association

**Impact:** Medium-high to high.

Detection is not just per-window classification. Radar systems form detections, associate them over time, and manage tracks.

**Technical work:**

* Add:

  * Kalman/extended Kalman/UKF/particle filters,
  * interacting multiple model filters,
  * track initiation/deletion logic,
  * missed-detection handling,
  * false-alarm handling,
  * gating,
  * JPDA/MHT-style association where relevant,
  * track-before-detect for weak targets.
* Simulate track breaks caused by clutter, occlusion, low SNR, and maneuvering.

**Acceptance gate:** Report track-level metrics separately from detection-window metrics.

## 18. P1 — Domain randomization must be causal and correlated

**Impact:** Medium-high.

The config uses broad independent parameter ranges. Real physics variables are correlated: altitude, speed, attitude, aspect, RPM, SNR, range, clutter, weather, and sensor geometry are not independent.

**Technical work:**

* Replace independent uniform boxes with hierarchical generative models:

  * site-level random effects,
  * weather-level random effects,
  * sensor-level random effects,
  * object-family random effects,
  * sortie/trajectory random effects.
* Use causal scene graphs.
* Fit priors from measured data where possible.
* Use uncertainty intervals, not single “best” values.

**Acceptance gate:** Holding out one site/weather/sensor family should cause plausible domain shift.

## 19. P1 — Simulator uncertainty and sensitivity analysis

**Impact:** Medium-high.

EchoForge mentions uncertainty-scored artifacts, which is the right direction. But uncertainty must propagate through detection metrics, not just sit on cards. ([GitHub][1])

**Technical work:**

* Add Sobol/global sensitivity analysis:

  * Which parameters dominate detection probability?
  * Which dominate false alarms?
  * Which dominate classifier score?
* Run posterior predictive checks against measured data.
* Maintain uncertainty distributions over RCS, clutter, propagation, weather, and receiver parameters.
* Report performance bands, not single AUCs.

**Acceptance gate:** The report should say, for example, “under this validated parameter posterior, (P_d) lies between X and Y at this false-alarm rate,” rather than “AUC = 1.0.”

## 21. P2 — Public benchmarks and external datasets

**Impact:** Medium.

Use public measured datasets as reality checks, even if they are not exact matches to your target scenario. The point is not to match one vehicle perfectly; it is to expose the simulator to real radar artifacts. Public radar/RF drone datasets and bird/drone micro-Doppler studies show measured data is messy, class-overlapping, and far from perfect separability. ([Nature][4])

* Train measured-only, test synthetic.

# Concrete EchoForge remediation plan

## Immediate fixes before another training run

1. **Delete all label-adjacent fields from model tables**: `object_class_id`, `classification_prior`, `sensor_observables`, expected range/Doppler bins, preset names, scenario names, seeds, target SNR, horizon name, and any future-derived summary.
2. **Use group holdout only**: hold out full scenario hashes, object families, environment families, sensor configs, and seeds.
3. **Train a metadata-only model**. It must fail.
4. **Train a noise-only / shuffled-label model**. It must fail.
5. **Make the baseline honest**: report the exact feature used by the baseline. A baseline AUC of 0.9995 at 45 s means your generator likely exposes targetness directly.

# Minimum acceptance gates before trusting any new AUC

I would require all of these before treating a result as meaningful:

| Gate                           |                                  Required result |
| ------------------------------ | -----------------------------------------------: |
| Metadata-only model            |                                       AUC ≤ 0.55 |
| Shuffled-label model           |                                       AUC ≈ 0.50 |
| Same-seed leakage check        |          No shared generator seeds across splits |
| Same-scenario leakage check    |          No shared scenario hashes across splits |
| Same-object leakage check      |     Hold out full object families/configurations |
| Same-environment leakage check |  Hold out full environment/site/weather families |
| Measured-data test             |       Reported separately from synthetic holdout |
| Baseline disclosure            |       Exact baseline score and inputs documented |
| Realistic base-rate evaluation | False alarms/hour and false tracks/hour reported |
| Causal horizon check           |    No future samples or future-derived summaries |

## Bottom line

Your current result is almost certainly **simulator separability or leakage**, not real-world radar predictive performance. The highest-impact work is not a better neural architecture; it is a stricter simulator/evaluation contract:

**raw complex radar observables only → causal labels only → group-held-out scenarios only → measured-data anchoring → radar-native metrics.**

Once those are in place, I would expect AUCs to drop sharply. That would be good news: it would mean the benchmark has started to resemble the real problem.
