## Bottom line

Those AUCs are a red flag, not a breakthrough. With holdout AUC ≈ 1.0 across CatBoost, LightGBM, CFAR/TBD fusion, TCN, and a transformer, plus baseline AUC already 0.966–0.9995, the simulator/evaluation is almost certainly creating a separable artifact: fixed SNR, fixed kinematics, leakage through horizon labels, post-detection features, seed/scenario overlap, overly clean negatives, or all of the above.

I can’t honestly claim to have studied **literally every online publication** on radar simulation, but I did a broad scan of the repo and the relevant open literature families: small-UAV radar detection/classification, RCS, micro-Doppler, clutter, propagation, multipath, RF-chain impairments, CFAR/tracking, sim-to-real validation, and radar sensor model validation. The report below is ranked by **expected impact on your AUC=1.0 failure mode**, not by academic elegance.

I’m also keeping this at the simulator-fidelity and defensive validation level. I am not providing adversary-specific targeting, defeat, or sensor-deployment tactics for a named country’s systems.

# 2. Why AUC≈1.0 is happening

Your table strongly suggests the classifier is not learning “real-world radar detection.” It is learning a simulator shortcut. The biggest clue is that the **baseline** is already near perfect: 0.9656 at 5 s, 0.9892 at 15 s, and 0.9995 at 45 s. When the baseline is that high, advanced models merely polish an already trivial signal.

Likely shortcuts include:

1. **Fixed target SNR**: the simulator computes target amplitude from a configured `target_snr_db`, AWGN sigma, and scalar RCS. That can create a stable amplitude signature that is independent of true geometry, aspect, clutter, and atmosphere. ([GitHub][5])

2. **Deterministic trajectory**: the default takeoff path has fixed range, heading, speed, acceleration, climb, and sinusoidal pitch/yaw perturbations. A model can learn the generator, not the physics. ([GitHub][5])

3. **Weak negatives**: if negatives do not match positives in range, Doppler, RCS scale, clutter, weather, horizon, and sensor state, detection becomes a nuisance-variable classification problem.

4. **Post-detection leakage**: using features such as detection count, CFAR confidence, max integrated power, target range bin, target state, or horizon-derived metadata can leak the answer.

5. **Row-level splitting instead of scenario-level splitting**: if samples from the same seed, trajectory, target model, clutter field, or sensor config are present in train and holdout, holdout is not independent.

6. **Unphysical clutter/noise**: real small-UAV radar is hard because clutter can come from buildings, ground/sea surfaces, moving vehicles, wind turbines, foliage, birds, terrain, and weather; clutter cross-section can be orders of magnitude larger than the target. The current simulator’s simple Gaussian/correlated clutter and few glints are far too separable. ([arXiv][9])

Real small-UAV radar is difficult precisely because target RCS depends on frequency, polarization, illumination angle, geometry, and material; motion includes velocity, attitude, climb rate, and micro-Doppler; and clutter/weather/terrain can dominate the return. ([arXiv][9])

# 3. Ranked technical work, highest impact first

## 1. Fix data leakage, split leakage, and shortcut learning before touching physics

**Impact: extreme.** This is the first thing to audit because AUC≈1.0 across unrelated model families almost always means the task is leaking or too clean.

Your holdout must be independent at the **episode/scenario/site/sensor/target/weather** level, not just the row level. A row split can leak the generator through repeated seeds, repeated kinematic profiles, repeated target states, repeated clutter fields, or repeated waveform/noise regimes.

Technical work:

* Run a **univariate AUC scan** over every feature: max range-profile amplitude, detection count, CFAR confidence, threshold, range bin, target state, horizon, SNR, seed-derived fields, number of glints, noise settings, and any metadata. Any single feature with AUC > 0.75 is suspicious; >0.9 is probably a shortcut.
* Run **label-shuffle tests**. Shuffled labels should produce AUC ≈ 0.5. Anything higher means leakage.
* Run **seed-only and config-only models**. Train using only seed, scenario ID, horizon, config, noise profile, and metadata. If AUC is high, the split is contaminated.
* Run **artifact-only baselines**: logistic regression on max amplitude, range-bin index, detection count, and CFAR confidence. If that matches CatBoost, the ML stack is not adding real value.
* Use **GroupKFold / leave-one-domain-out** splits: hold out entire target geometries, material cards, weather regimes, terrain tiles, clutter seeds, sensor configs, and trajectory families.
* Use **paired counterfactual episodes**: same sensor, same terrain, same weather, same clutter, same time, same RFI, but target absent/present or replaced by a matched confuser.
* Ban post-label fields: target state, true range, true altitude, generator class, synthetic `target_snr_db`, horizon-derived metadata, and any post-CFAR target-confirmation field should not be used for early prediction unless they are genuinely observable at that horizon.

This should be your acceptance rule: a model is not allowed to score above chance on metadata-only or seed-only features, and a simple max-power baseline must not be near-perfect. Your current baseline AUCs indicate this rule would probably fail.

## 2. Replace fixed SNR and scalar target amplitude with a physically derived radar budget

**Impact: extreme.** Fixed SNR is one of the fastest ways to create fake AUC.

In the current simulator, target amplitude is derived from `target_snr_db`, AWGN sigma, and scalar RCS. That makes target detectability more like a configured label than an emergent result of range, target aspect, antenna gain, propagation, clutter, receiver state, and processing gain. ([GitHub][5])

Technical work:

* Remove `target_snr_db` as a direct generator control for labeled examples.
* Compute received power from a radar equation budget: transmitted power or EIRP, antenna pattern, two-way path loss, target RCS, polarization mismatch, propagation loss, system noise temperature, receiver noise figure, bandwidth, integration time, processing gain, and clutter/interference power.
* Make SNR/SCR/SINR an **output diagnostic**, not an input knob.
* Sample sensor state: calibration drift, temperature, receiver gain, AGC state, saturation margin, timing jitter, ADC quantization, and dynamic range.
* Generate plenty of cases where the target is below threshold, partially visible, intermittently visible, or masked by stronger clutter.

Real UAV detection studies emphasize that small RCS, slow speed, and low altitude make small drones challenging, and SNR-only detectors can miss weak drone returns; Doppler signal-to-clutter approaches were proposed specifically because traditional SNR approaches can fail in these regimes. ([MDPI][10])

## 3. Replace scalar RCS with aspect/frequency/polarization/material-dependent RCS

**Impact: extreme.** A scalar `rcs_scalar` is not remotely sufficient.

The open literature is very clear: UAV RCS depends on operating frequency, polarization, illumination/aspect angle, geometry, and electrical material properties. The UAV survey explicitly lists frequency, polarization, angle of illumination, geometry, and material as RCS drivers. ([arXiv][9])

Your object card has only a fixed public-proxy geometry and your material card has a single composite baseline over 1–40 GHz. That is a placeholder, not an RCS model. ([GitHub][4])

Technical work:

* Build RCS as a multidimensional lookup or surrogate:
  `σ(frequency, azimuth, elevation, polarization_tx, polarization_rx, attitude, material_state, propulsor_state)`.
* Separate **mean RCS**, **scintillation**, and **glints**. Use Swerling-style or compound distributions where appropriate, but do not pretend one distribution fits all geometries.
* Validate against canonical scatterers first: sphere, flat plate, dihedral, trihedral, cylinder, cone.
* Then cross-check with independent EM solvers before using target-like geometries.
* Include mesh convergence studies, frequency sweeps, polarization basis checks, material uncertainty, roughness, edges, cavities, seams, landing gear/launch hardware, and rotating propulsors.
* Treat fixed-wing and multirotor UAVs separately. Fixed-wing RCS signatures can be much smaller than familiar quadcopters and vary strongly by aspect.

A fixed-wing UAV RCS study found mean RCS values around −17.62 dBsm in one X-band scenario and −22.77 dBsm across a broader 3–16 GHz scenario for a 2 m class fixed-wing UAV, smaller than a DJI Inspire 1 in the same study. The authors also stress limitations: many variables, limited frequency/angle coverage, default material assumptions, and stationary propellers in the simulator. ([MDPI][11])

## 4. Replace deterministic takeoff kinematics with stochastic, physically plausible motion ensembles

**Impact: very high.** Your default takeoff is too smooth and too identifiable.

The current `TakeoffProfile` has fixed initial range, heading, speed, acceleration, climb rate, max altitude, radial velocity bias, sinusoidal pitch/yaw jitter, propulsor frequency, and micro-Doppler frequency. A model can memorize this synthetic family. ([GitHub][5])

Technical work:

* Create trajectory families, not one profile: ground roll, rail/catapult-like launch, hand/vehicle launch, climb-out, turn, level segment, terrain-following segment, aborted/partial launches, and occluded starts. Keep these generic and non-adversary-specific.
* Sample acceleration, jerk, climb, heading change, attitude dynamics, yaw/roll/pitch, wind drift, turbulence, engine/prop RPM variation, and sensor line-of-sight angle.
* Model low-altitude visibility: terrain masking, buildings, vegetation, launch-site clutter, horizon, and beam elevation.
* Produce “near twins”: false targets with similar range, Doppler, altitude, and RCS but different micro-Doppler/trajectory semantics.
* Hold out entire trajectory families in validation.

The survey literature notes that relevant motion characteristics include velocity, pitch, yaw, roll, rate of climb, and micro-Doppler from moving subparts. It also emphasizes that classification uses size, shape, velocity, maneuverability, propeller motion patterns, and altitude-dependent features. ([arXiv][9])

## 5. Build real clutter, not Gaussian background plus a few glints

**Impact: very high.** Clutter is probably the largest missing reality factor.

The current noise profile has AWGN, scalar clutter sigma/correlation, RFI probability, and a few ground glints. That is not a real clutter field. ([GitHub][5])

Real radar clutter includes specular and diffuse reflections from buildings, man-made structures, birds, trees, hills, ground/sea surfaces, moving vehicles, aircraft, wind turbines, and foliage. The survey notes that clutter can be static or dynamic, and that clutter cross-section can be thousands of times larger than an aerial vehicle’s cross-section. ([arXiv][9])

Technical work:

* Model **terrain-linked clutter** using DEM/DTED, land cover, surface roughness, slope, vegetation, buildings, roads, towers, wires, vehicles, and water.
* Use **range-Doppler-angle clutter maps**, not independent scalar noise.
* Add nonhomogeneous clutter: clutter edges, shadow zones, bright reflectors, moving ground targets, foliage motion, bird flocks, insects, wind turbines, and precipitation.
* Use heavy-tailed clutter models where appropriate: Weibull, K-distribution, log-normal, compound-Gaussian, texture/speckle models, and empirically fitted mixtures.
* Make clutter correlated across time, range, Doppler, angle, polarization, and sensor scan.
* Generate hard negatives from the same nuisance distribution as positives.

The key simulation principle: positives and negatives must share the same nuisance variables. If positives are “target plus clean noise” and negatives are “empty clean noise,” AUC=1 is expected.

## 6. Add low-altitude multipath, terrain masking, and ground-bounce physics

**Impact: very high.** Low-altitude radar without multipath is not credible.

Your current signal path is essentially direct-path delay plus simple glints. Real low-altitude radar returns can include direct path, ground-reflected path, diffuse multipath, terrain/building reflections, shadowing, ghost detections, phase lobing, and range/angle biases. ([GitHub][5])

Technical work:

* Add two-ray ground reflection as the minimum baseline.
* Add specular and diffuse multipath from terrain, buildings, vehicles, water, and other large reflectors.
* Include ground permittivity/conductivity, surface roughness, grazing angle, polarization, and seasonal moisture state.
* Simulate ghost targets, altitude bias, range bias, intermittent cancellation, and false tracks.
* Use ray tracing, parabolic-equation propagation, or hybrid methods for complex terrain.
* Validate with simple measured scenes before complex scenes.

Multipath simulations are described in the literature as necessary for capturing radar–target–environment interactions; classic validation work also emphasizes environment models containing reflecting/shadowing obstacles, terrain features, and antenna locations. ([arc.aiaa.org][12])

## 7. Add weather and atmospheric propagation

**Impact: high.** Weather is not just attenuation; it is also clutter and propagation distortion.

The UAV radar survey states that propagation differs across terrain and atmospheric conditions, and that rain, hail, snow, fog, precipitation, wind in forests, and strong sea air currents can affect radar detection and propagation. ([arXiv][9])

Technical work:

* Add gaseous absorption, humidity, pressure, temperature, refractivity gradients, bending, evaporation ducts, and anomalous propagation.
* Add rain attenuation and rain clutter; use ITU-R P.838-style rain specific attenuation as one standard component.
* Add fog/cloud attenuation where relevant to higher frequencies.
* Add weather-dependent surface reflectivity: wet ground, dry ground, snow, dust, sea state, vegetation motion.
* Model weather as time-varying fields, not a static label.

ITU-R P.838-3 provides a standard rain specific attenuation model using a power-law relationship between rain rate and attenuation. ([ITU][13])

## 8. Model the RF hardware chain, not just ideal chirps

**Impact: high.** The current waveform/receiver is far too clean.

The current primitive chain is LFM chirp generation, matched filtering, magnitude, and 1D CA-CFAR. ([GitHub][14])

Real radar simulation work models the transmit chain, propagation/environment, receive chain, and data-processing chain, then validates range-Doppler plots against real radar trials. Whole-system radar modelling papers emphasize phase noise as especially important for slowly moving, low-RCS targets in strong clutter. ([University of Birmingham][15])

Technical work:

* Model transmitter: chirp nonlinearity, phase noise spectrum, timing jitter, PA nonlinearity, pulse shaping, spurs, temperature drift.
* Model receiver: LNA noise figure, mixer leakage, I/Q imbalance, ADC quantization, clipping, AGC, dynamic range, filtering, baseband bandwidth, synchronization, dropped pulses.
* Model leakage/self-mixing, especially for FMCW-like architectures.
* Model calibration: antenna phase/gain errors, boresight errors, clock errors, time sync, channel imbalance.
* Make hardware impairments parameterized by realistic distributions and validated against measured hardware.

Phase noise is a fundamental radar impairment, and FMCW phase-noise modeling literature explicitly focuses on predicting the phase-noise level in radar displays, including practical measurements for validation. ([the University of Bath's research portal][16])

For FMCW systems, transmit/receive leakage can appear as a strong near-range target due to non-ideal isolation, radome/body reflections, and antenna effects; this degrades dynamic range and can mask weak targets. ([E-Technik Uni Ulm][17])

## 9. Add antenna, beam, polarization, scan, and array effects

**Impact: high.** Without antenna physics, the simulator misses a major source of variability.

Real detectability depends on beamwidth, sidelobes, scan schedule, dwell time, polarization, antenna height, elevation coverage, array calibration, and angular resolution. The UAV survey explicitly connects clutter strength to angular/range resolution and notes that classification depends on range/angular resolution and clutter rejection capability. ([arXiv][9])

Technical work:

* Add antenna gain patterns, sidelobes, backlobes, polarization basis, scan loss, beam squint, and elevation coverage.
* Model dwell time and scan revisit: a target may be seen intermittently depending on scan timing.
* Add angle estimation uncertainty and angle-Doppler coupling.
* For arrays, model element spacing, mutual coupling, calibration drift, failed elements, digital beamforming, MIMO virtual arrays, and DOA estimation errors.
* Make target/clutter returns pass through the same beam and scan schedule.

This is also a major leakage source: if all positives occur in one beam state and all negatives in another, ML will learn the beam state, not the target.

## 10. Replace magnitude-Doppler proxy with a coherent range-Doppler-angle data cube

**Impact: high.** The current Doppler proxy is not physically correct.

The simulator computes pulse-compressed magnitudes and then runs a slow-time DFT over magnitudes. That loses coherent phase, which is essential for Doppler, clutter cancellation, velocity ambiguity, micro-Doppler, and coherent integration. ([GitHub][5])

Technical work:

* Preserve complex IQ through the full chain.
* Build a radar data cube: fast time × slow time × channel/angle.
* Apply windowing, coherent integration, Doppler FFT, clutter cancellation/MTI/MTD, Doppler ambiguity handling, range migration correction, and sidelobe control.
* Include pulse-to-pulse phase noise, timing jitter, PRI jitter, missed pulses, and CPI boundaries.
* Derive range-Doppler maps from complex slow-time data, not magnitudes.

The literature on UAV detection frequently relies on range-Doppler maps, micro-Doppler spectrograms, Hough transforms, CNNs over range-Doppler patches, and multi-frame information, which all require a more faithful coherent processing chain than the current proxy. ([arXiv][9])

## 11. Replace one sinusoidal micro-Doppler term with physical micro-motion

**Impact: high for classification, medium-high for detection.**

The current simulator has `propulsor_hz` and `micro_doppler_hz` fields and modulates amplitude with a simple sinusoid. ([GitHub][5])

Real micro-Doppler is generated by rotating propellers, flapping wings, structural vibration, and relative motion of subcomponents. Drone/bird studies show that RCS alone is not adequate because birds can have similar size, altitude, and speed; coherent radar micro-Doppler is important for discrimination. ([Nature][18])

Technical work:

* Model blade count, RPM distributions, RPM jitter, pitch, hub location, blade material, blade aspect, and orientation relative to radar.
* Include body motion plus rotating components, not just amplitude modulation.
* Generate spectrograms with STFT/CWT choices, CPI length, windowing, and SNR/clutter effects.
* Model bird wingbeat confusers with species/size/flock distributions.
* Avoid using micro-Doppler in a way that trivially labels all drones and no negatives; birds, insects, helicopters, wind turbines, and other rotating/moving objects can produce structured signatures too.

Experimental K-band/W-band studies found drone signatures with rotor blade flash and HERM lines, while birds show periodic wingbeat flashes; the relative strength varies by target, aspect, frequency, and measurement setup. ([Nature][18])

# 4. Specific likely simulator artifacts causing your perfect scores

Here is the most probable failure stack for your current result:

1. **Target amplitude is too deterministic.**
   `target_snr_db` and scalar RCS likely make target-present examples consistently brighter than target-absent examples. ([GitHub][5])

2. **Target range/trajectory is too deterministic.**
   Fixed initial range and fixed motion create a learnable range-bin/time pattern. ([GitHub][5])

3. **Doppler/micro-Doppler is synthetic and class-pure.**
   One micro-Doppler sinusoid is unlikely to be shared by hard negatives. ([GitHub][5])

4. **Clutter is not strong enough and not structured enough.**
   Real clutter can dominate small-UAV returns by orders of magnitude; scalar correlated Gaussian clutter is far easier. ([arXiv][9])

5. **Hard negatives are not matched.**
   Birds, foliage, vehicles, wind turbines, civilian drones, and weather need to occupy the same feature space as positives. ([Nature][18])

6. **Holdout likely shares generator structure.**
   With train/validation/holdout all drawn from the same narrow synthetic generator, “holdout” only tests interpolation.

7. **Baseline AUC is already near perfect.**
   This is the clearest signal that a simple statistic is solving the task.

8. **Horizon formulation may leak time-to-target or target presence.**
   If horizon labels are derived from deterministic range/altitude/trajectory state, models may infer horizon from geometry rather than detectability.

9. **CFAR output may be used as a feature for detection labels.**
   If the label is “target detectable” and the feature is “detector confidence,” that is circular.

10. **No measured-data challenge set exists.**
    Without measured measured validation, AUC only says the model matches the simulator, not reality. ([GitHub][2])

# 5. Immediate test plan to prove or disprove leakage

Run these before adding any more physics.

## A. One-feature AUC audit

Compute AUC for each feature alone:

* max integrated range-profile amplitude
* mean integrated range-profile amplitude
* top-k peak ratio
* CFAR detection count
* max CFAR confidence
* range bin of max power
* estimated range
* threshold/noise estimate
* seed
* scenario ID
* horizon
* noise profile fields
* target profile fields
* target state fields
* any post-CFAR or post-label features

If any one feature gives AUC > 0.9, quarantine it.

## B. Metadata-only classifier

Train CatBoost/LightGBM on metadata only. Expected AUC: ≈0.5. If it is high, your split is contaminated or the generator is encoding labels in config.

## C. Seed-only classifier

Train on seed and derived seed bucket only. Expected AUC: ≈0.5. If it is high, seed ranges or scenario generation are label-correlated.

## D. Matched no-target counterfactuals

For every positive episode, create:

* same terrain
* same weather
* same clutter
* same RFI
* same radar state
* same scan schedule
* same time
* same noise realization where possible
* target removed

The model should no longer win by nuisance variables.

## E. Confuser-matched negatives

Create negatives with matched range, radial velocity, altitude, RCS range, Doppler spread, and clutter cell. Use birds, civilian drones, ground movers, and multipath ghosts. This is where real difficulty begins.

## F. Leave-one-family-out validation

Hold out entire:

* target geometry family
* material family
* trajectory family
* clutter/site family
* weather family
* sensor configuration
* hard-negative class

AUC should drop. If it does not, the test is still too easy or still leaking.

## G. Sim-to-real mini-gate

Even a tiny lawful measured dataset is useful. Train on sim, test on measured; train on measured, test on sim; compare intermediate radar products, not just labels. Recent radar sim-to-real work emphasizes that synthetic-to-real radar transfer must be quantified and validated, not assumed. ([arXiv][20])

# 6. Publication-backed checklist of missing real-world artifacts

## Target and signature artifacts

* Aspect-dependent RCS
* Frequency-dependent RCS
* Polarization-dependent RCS
* Material-dependent RCS
* RCS scintillation and glints
* Propeller/rotor/engine micro-Doppler
* Fuselage/wing/body scattering
* Stationary vs rotating propulsor differences
* Attitude-dependent signature changes
* Structural vibration
* Launch hardware or ground interaction
* Manufacturing variation
* Damage, dirt, paint, moisture, payload variation

RCS dependence on frequency, polarization, aspect, geometry, and materials is a core point in UAV radar literature; fixed-wing UAV RCS studies also emphasize that RCS work has many limitations and that propeller rotation may not be represented in common simulation tools. ([arXiv][9])

## Environment artifacts

* Terrain elevation and local horizon
* Buildings and man-made structures
* Roads and moving vehicles
* Trees, foliage, wind motion
* Ground/sea clutter
* Water glints
* Wet/dry/snow-covered surfaces
* Urban canyon reflections
* Towers, fences, wires, cranes
* Wind turbines
* Birds, flocks, insects
* Weather cells and precipitation clutter

The UAV survey identifies buildings, man-made structures, birds, trees, hills, ground/sea reflection, moving vehicles, planes, wind turbines, and foliage as clutter sources, and states clutter cross-section can be much larger than UAV cross-section. ([arXiv][9])

## Propagation artifacts

* Free-space loss
* Atmospheric absorption
* Rain attenuation
* Fog/cloud attenuation at higher frequencies
* Refraction and bending
* Ducting/anomalous propagation
* Diffraction around terrain
* Ground bounce
* Multipath ghosting
* Shadowing/occlusion
* Grazing-angle effects
* Surface roughness and dielectric effects

Rain attenuation can be modeled using ITU-R P.838-3, while multipath literature emphasizes reflecting/shadowing obstacles, terrain features, and antenna locations for validated simulations. ([ITU][13])

## Sensor artifacts

* Antenna pattern and sidelobes
* Polarization mismatch
* Beam scanning and dwell
* Array calibration errors
* Channel gain/phase imbalance
* Oscillator phase noise
* Chirp nonlinearity
* Timing jitter
* PRI jitter
* Pulse dropouts
* ADC quantization/clipping
* AGC and dynamic range
* I/Q imbalance
* TX/RX leakage
* Radome effects
* Temperature drift
* Receiver noise figure
* Clock synchronization
* RFI/interference from other emitters

Whole-system radar modelling and FMCW phase-noise papers emphasize modeling transmit/receive/data-processing chains and phase-noise effects, especially for slowly moving low-RCS targets in strong clutter. ([University of Birmingham][15])

## DSP artifacts

* Complex IQ preservation
* Matched-filter sidelobes
* Windowing loss
* Coherent processing interval
* Range-Doppler ambiguity
* Doppler wrapping
* Range migration
* MTI/MTD clutter cancellation
* 2D/3D CFAR
* Clutter maps
* Track-before-detect
* Multi-frame integration
* Association and track management
* False-track logic
* Multi-sensor fusion

The UAV survey includes a wide range of detection/classification/tracking approaches—CFAR, CNNs on range-Doppler patches, Hough transforms, multi-frame information, multistatic radar, passive radar, and micro-Doppler—showing that realistic systems are far beyond 1D CA-CFAR on an integrated profile. ([arXiv][9])

# 7. What “most accurate simulator” should mean here

The goal should not be “simulate one exact named drone with exact real signatures” unless you have lawful measured data and authorization. The safer and scientifically stronger goal is:

> Simulate a distribution of small fixed-wing, propeller-driven, low-altitude UAV-like targets with explicit uncertainty, validated against lawful measured radar data, and tested against matched hard negatives under realistic clutter, propagation, weather, and sensor imperfections.

That approach aligns with your own repo’s public-proxy/no-measured-truth governance stance. ([GitHub][1])

# 8. Recommended rebuild order

## Phase 1 — Stop the fake AUC

1. Remove all target-state, seed, scenario, config, and post-detection leakage from model features.
2. Add metadata-only, seed-only, one-feature, and label-shuffle tests.
3. Use group splits by scenario family, seed family, target family, site, weather, and sensor config.
4. Add paired no-target counterfactuals.
5. Report PD@PFA, false alarms/hour, false tracks/hour, and time-to-detect, not just AUC.

## Phase 2 — Make negatives real

1. Add matched birds, flocks, civilian drones, ground movers, wind turbines, foliage, weather, and multipath ghosts.
2. Match negatives to positives on range, Doppler, altitude, RCS, clutter, and sensor state.
3. Keep a never-seen hard-negative challenge set.

## Phase 3 — Replace scalar physics

1. Replace scalar RCS with aspect/frequency/polarization/material tables.
2. Replace fixed SNR with radar-budget-derived received power.
3. Preserve complex IQ and build a coherent range-Doppler-angle cube.
4. Add terrain-linked clutter and multipath.
5. Add RF-chain impairments.

## Phase 4 — Validate

1. basic: canonical scatterers.
2. cross_checked: cross-solver RCS and propagation checks.
3. benchmarked: controlled lab/range data.
4. benchmarked: controlled outdoor site trials.
5. measured: lawful measured data with provenance.

Radar sensor validation literature increasingly emphasizes direct comparison between simulated and real radar data and separating environment, propagation, and signal-processing errors. ([Springer][21])
